Job schedule

Running a job by itself, at set times, on one machine.

A schedule runs a job by itself: once, every so often, or on the days and at the times of a cron pattern. Schedules are part of the project, so every copy that opens it sees the same ones. Each names the one machine that runs it.

The Job schedule pane shows them on a line of time: the runs that happened to the left of now, the times to come to the right. dbdb-cli schedule list and the list_schedules tool say the same in text and JSON.

The settings of a schedule are in the panel under the timeline, the same panel the Job designer has for a step. A schedule that was just added has them on show, and so does one whose name on the timeline is clicked. The panel folds down to its tab, to leave the room to the timeline.

What a schedule holds

{
  "name": "nightly load",
  "job": "load_customers",
  "machine": "etl-server",
  "when": {"kind": "cron", "cron": "0 2 * * *"},
  "time_zone": "Europe/Zurich",
  "environment": "production",
  "missed": "run"
}
Field Meaning
name What the schedule is called
job The job to run
machine The machine that runs it. Empty: no machine does
when When it runs; see below
time_zone The clock its times are told on, such as Europe/Zurich. Left out, the zone of the machine that adds it
environment The environment whose values the run uses; left out, the defaults
parameters Values for single parameters, which win over the environment's
missed skip (the default) or run; see "Missed times"
paused true keeps the schedule and does not run it
until The last time it may run at, as 2026-12-31 23:59 on its clock
since Set by dbdb: the moment the schedule counts from. A time before it is neither run nor shown as missed

when is one of three:

kind Fields Runs
once at: 2026-11-20 08:00 One time
every every, unit (minutes, hours, days, weeks), from Again and again, counted from from. Days and weeks keep the time of day of from
cron cron: 0 6 * * 1-5 On the days and at the times of the pattern

A cron pattern has five fields: minute, hour, day of the month, month and day of the week. A field is *, a number, a range 1-5, a list 1,15, or any of them with a step, */10. Months and days of the week can be named (jan, mon); Sunday is 0 or 7; L as the day of the month is its last day. When both the day of the month and the day of the week are given, a day that fits either counts. @hourly, @daily, @weekly, @monthly and @yearly are read too.

In the pane nobody has to write a pattern: Hourly, Daily, Weekly and Monthly ask for the days and the time and write it. Custom takes any pattern, and the pane says it back in words with its next times.

The commands are add_schedule, update_schedule, rename_schedule and remove_schedule, from the pane, dbdb-cli apply and the apply_command tool alike. A job that is renamed keeps its schedules.

The machine

A machine is known by the computer's name, or by the DBDB_MACHINE variable when it is set, compared without regard to capitals. It is the same name the Connectors pane uses. The pane and dbdb-cli schedule list say what this machine is called.

Who runs a schedule

A schedule runs only while a runner is there on its machine. There are three:

  • The app, while it is open with the project, once Run here is ticked in the pane. The tick is for this copy and this project; it is saved with the app and never in the project, so opening a shared project does not start jobs on a machine by itself. When a project with the tick is opened again, a window says that this machine runs its jobs, and offers to stop. If the project is no longer the one the tick was given for, as after it was shared with a new key, nothing runs until you say so again (sharing-and-trust.md). The app runs one job at a time: a schedule that comes due during a run starts when that run is over.
  • dbdb-cli schedule run project.json, without the app. It looks at the clock once a minute, reads the project file again each time, and runs what is due. It runs until it is stopped.
  • dbdb-cli runner project.json, without the app and synced with the project's other copies. It does what schedule run does, and follows what other copies change through the project's relay too, so a schedule changed in a browser is the one that runs without the file being carried over. It also runs what other copies ask of this machine: see remote-runs.md.

dbdb-cli schedule run project.json --once looks once, runs what is due and exits, for a system that calls it every minute:

# cron
* * * * * dbdb-cli schedule run /srv/etl/project.json --once

# systemd: dbdb-schedule.service
[Service]
ExecStart=/usr/local/bin/dbdb-cli schedule run /srv/etl/project.json
Restart=on-failure

With --once the exit status is 1 when written data has issues and 2 when a run failed. --machine NAME runs the schedules of another name.

The browser build shows the schedules and their runs, and can change them, but never runs one: a page that is closed keeps no time.

Never twice

Before it runs a job, a runner takes the schedule's time: it makes a file in runs/claims beside the project, which only one program can make. The app and dbdb-cli, both running on one machine, then run a time once between them. So do two machines that were given the same name and work on the same folder.

Missed times

A time is missed when it passed while the machine was off or asleep, or no runner was there.

  • skip, the default: it is not run. The pane shows it as missed, and Run now on it runs it after all.
  • run: it runs once, as soon as a runner is back. A schedule that was due five times meanwhile runs once, not five times.

Time zones and summer time

The times of a schedule are times on the clock of its time zone, so six in the morning stays six in the morning when summer time begins or ends, on whichever machine looks at it.

  • A time the clock skips on the night summer time begins runs at the first moment after the gap.
  • A time that comes twice on the night it ends runs once, the first time. A pattern for every hour runs in both hours.

Past runs

A scheduled run leaves a run record like any other (runs.md), in the runs folder beside the project file, with three things more: machine, and under scheduled the schedule and the time it was due. Nothing of a run is written to the project file, which would otherwise change with every run.

The line of time shows what is in that folder. Machines that share the folder see each other's runs. Copies that are synced only through a relay share the schedules but not the runs folder, so each sees the runs made on its own machine. A run that a copy asked another machine for is the exception: its record comes back with the answer (remote-runs.md).

From the command line and for an assistant

dbdb-cli schedule list project.json                  # each schedule, its next time, last run and what it missed
dbdb-cli schedule list project.json --json --days 14
dbdb-cli schedule run project.json                   # run this machine's schedules until stopped
dbdb-cli schedule run project.json --once            # look once, run what is due, exit
dbdb-cli runner project.json                         # the same, synced, and what other copies ask of this machine

The list_schedules tool gives the JSON of schedule list: for each schedule what it says in words, whether this machine runs it, its next time, its last run and the times it missed, then the times to come and the latest runs.
