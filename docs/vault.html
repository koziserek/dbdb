The vault

Where passwords live, and how they travel sealed.

A project file is text that everyone with the project can read, and it travels: through a shared folder, a relay, a browser, git, an email. A password typed into a connection travels with it.

The vault is the place in a project for such values. A secret has a name in plain text and a value that is sealed with a password of your choice. Everyone who has the project and the password can use the secrets. Nobody else can read them, in the file or anywhere it goes.

"vault": {
  "id": "29a5223690c3",
  "lock": "argon2id$m=65536,t=3,p=1$qLWc…$daRk…",
  "secrets": [
    {"name": "pg_prod", "id": "9d414374d7be", "sealed": "7o7IAYjR…"}
  ]
}

Using a secret

Write ${vault:name} where the secret goes in a connection:

{"kind": "postgres_table", "url": "postgresql://etl:${vault:pg_prod}@db.example.org/sales", "table": "public.orders"}
  • It works in the connection of a source and of a database output, and in a parameter that a connection uses, so test and production can each have their own secret (see parameters).
  • It works nowhere else. A secret in a path, a query or an expression could end up in an output file, so validate refuses it there.
  • In a URL the value is encoded for you: a password with @ or / in it is typed into the vault as it is.
  • A connector to a model can take its key from a secret: set key_secret to the secret's name, and the connection of a connector to a database takes its password as ${vault:name} like any connection (see connectors).

env:NAME stays, and stays the right choice for a value that differs from machine to machine: it is read from that machine's environment.

When the password is asked for

Opening a project, editing it, saving and syncing never ask. The vault has to be open only when something connects with a secret: reading or previewing such a source, running a job that uses one, or starting the Assistant with a connector whose key is in the vault.

  • App. The Vault window opens by itself the first time a secret is needed. Edit > Vault… opens it at any time. The vault stays open until dbdb closes or you choose Lock vault; the status bar shows 🔓 or 🔒. The password and the opened key are kept in memory only.
  • dbdb-cli at a terminal asks, without showing what you type.
  • dbdb-cli in a script, the MCP server, a schedule. Give the password in the variable DBDB_VAULT_PASSWORD, or as the first line of a file named with --vault-password-file. A password that is wrong is an error at once.

A job that needs a secret of a locked vault stops before it reads or writes anything, and names the secret:

error: `${vault:pg_prod}` is needed, and the vault is locked. Unlock it in the app (Edit > Vault), or give `dbdb-cli` its password in the variable DBDB_VAULT_PASSWORD or with --vault-password-file

A job that uses no secret runs with the vault locked.

A machine that runs jobs with nobody there has to hold the password somewhere, and a variable is no safer for it than env:NAME was. What changes is that it is one value for the machine instead of one for each connection.

Managing the vault

In the app, everything is in Edit > Vault…: make the vault, seal a secret, show or replace one, remove one, change the password, and move the passwords that are written in connections into the vault.

From the command line:

dbdb-cli vault project.json create              # asks for a password, twice
dbdb-cli vault project.json set pg_prod         # asks for the value, or reads it from standard input
dbdb-cli vault project.json status              # the secrets by name, and what uses each; no password needed
dbdb-cli vault project.json rename pg_prod pg   # the connections that name it follow
dbdb-cli vault project.json remove pg
dbdb-cli vault project.json move-in             # every password written in a connection or a connector becomes a secret
dbdb-cli vault project.json change-password
dbdb-cli vault project.json reset --forget-values

set never takes the value as an argument, which would stay in the shell's history.

The commands behind these (set_vault, set_vault_lock, set_secret, rename_secret, remove_secret) carry a value sealed, never in plain text. So the command log, undo, the sync and an assistant that applies commands only ever see what the file holds. An assistant can name a secret in a connection; it cannot read one or set one.

Moving passwords in. validate warns about each connection that holds a password in plain text. Move passwords to the vault (or vault move-in) seals each under the name of its source or connector and writes ${vault:name} in its place, as one step that one Undo takes back. The password is still in older copies of the file, in git and in the sync folder: change it at the database if the file was ever shared.

Changing the password

A new password rewrites one line, the lock, and no secret. The other copies of the project get it with the next sync and ask for the new password the next time they unlock.

It does not take back what an old copy could read: copies of the file from before still open with the old password. If the old password may be known to someone who should not have it, change the secrets themselves, at the database or the provider.

A lost password

There is no way back to a lost password. That is what the seal is worth.

What is lost is the values, and nothing else: the project opens and works as before. Lost the password? in the Vault window (or vault reset --forget-values) gives the vault a new password and keeps every secret's name with no value. Each connection still points at its secret, and the window lists the ones to enter again.

What it protects, and what not

  • Protected: the project file wherever it lies or goes, the sync folder, what a relay or a browser keeps, backups, git history, run records, and what an assistant is shown.
  • Not protected: the names of the secrets, and everything else in the project: hosts, user names, tables, queries, notes. The file stays readable on purpose, so that it can be compared, merged and worked on without the password.
  • A weak password. Whoever has the file can try passwords without limit, only slowly. Choose a long one.
  • An open vault. Whoever sits at the machine while the vault is open can use the secrets, and see them in the Vault window.

How it is sealed

  • Making a vault draws a random 256-bit vault key. It seals every secret with XChaCha20-Poly1305 and a fresh random nonce, and never changes.
  • The password becomes a second key through Argon2id, with a random salt, 64 MiB of memory and 3 passes. That key seals the vault key. The result is the lock, with the salt and the settings in it.
  • A secret is sealed together with the vault's id and its own id, so a sealed value copied under another secret, or into another vault, does not open.
  • A project with a vault is written as "format": 4, so that an older dbdb leaves it alone instead of saving it without its secrets (see shared projects).
