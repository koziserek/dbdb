Run history

The record every run leaves, and what it shows.

Every run of a job that writes leaves a record: one JSON file in the runs folder beside the project file. It is the evidence that a load ran, with what, and what it did, and it shows which step takes the time.

A record is made by Run job in the app and by dbdb-cli run-job. A check (Check outputs, --dry-run) writes nothing and leaves no record. A run that fails is recorded too, with its error.

What a record holds

  • the job, when it started (UTC) and how long it took
  • how it ended: ok, issues (the checks found problems in the written data), stopped (a sub-job's issues stopped the series) or failed
  • the environment and the parameter values used
  • for each job of the run, the job itself and then its sub-jobs: the time it took to read the sources, and for each step the rows it passed on, the rows it did not (a Filter's, or the ones an output rejected) and the step's own time. For an output step that is the time to write, and the record also has the file or table written, the number of issues and the first 100 of them
  • the dbdb version
  • for a run that went on from an earlier one (run-job --resume, "Run the rest"): resumed, the start of that earlier run, and kept on each sub-job that got through then and was not run again
  • for each sub-job, node: the number of the Sub-job step that ran it. Sub-jobs are listed in the order of their steps, also when several ran at the same time
{
  "job": "export",
  "started": "2026-11-12T16:42:46Z",
  "ms": 18.3,
  "result": "ok",
  "environment": "production",
  "parameters": { "db": "env:PROD_DB", "out": "/srv/export" },
  "dbdb": "0.12.0",
  "jobs": [
    {
      "job": "export",
      "read_ms": 11.8,
      "steps": [
        { "node": 1, "step": "Input", "source": "parts", "rows": 306, "ms": 0.07 },
        { "node": 2, "step": "Filter", "rows": 273, "rejected": 33, "ms": 0.55 },
        { "node": 3, "step": "File output", "wrote": "/srv/export/parts.csv",
          "rows": 273, "ms": 1.7, "issues": 0 }
      ]
    }
  ]
}

A password written into a connection (postgresql://user:password@host, password=...) is saved as ***. A value such as env:PROD_DB is kept, since it names the variable and not what is in it.

The file is named after the start time and the job, runs/20261112T164246Z-export.json, so the folder sorts by time. Nothing removes old records: delete or archive the files as you see fit.

The Runs pane

Add a Runs pane with the ➕ of any panel, or switch a pane to it. The upper part lists the runs, newest first, with time, rows written, rows rejected, issues and result; the list can be narrowed to one job. A click opens a run below: its environment and parameters, then every job with its steps. The slowest part of the run is marked.

The run is one table. Every job has a line of its own with what it and its sub-jobs wrote in all: rows, rejected rows, issues and time. Its steps follow, and the sub-jobs are set in under the job that ran them, with their numbers in the same columns. Both tables are as wide as the pane. In a narrow pane the names are cut short first; point at one to read all of it.

⟳ reads the folder again, for runs made meanwhile with dbdb-cli.

Going on from a run that stopped

A series of sub-jobs that failed or stopped part of the way need not run from the start again. "Run the rest" in the Job designer, dbdb-cli run-job ... --resume and resume of the run_job tool read the newest record of the job and run only what did not get through:

  • A sub-job that ran, with every job under it, is kept: it is not run again, and the new record lists it as kept.
  • The sub-job that failed runs again, and so do the ones that were skipped after it.
  • A sub-job that stopped the series with its issues runs again. Set its step to stop only on errors, and it is kept with its issues.
  • A series inside the series goes on from where it stopped in the same way.

The last run has to be with the same environment. Nothing else is compared: going on says that what the last run wrote still stands, so run from the start after a change to a job that was kept. A check leaves no record, so there is none to go on from.

A project that has not been saved has no folder to keep records in, and a browser page cannot write them: there the runs are listed until the app is closed.
