What sharing a project allows

What sharing a project hands over, and what a machine agrees to.

dbdb is made for a team that trusts each other: the people who build a migration, and the machines they run it on. A shared project has one permission, and it is all or nothing. This page says what you hand over with a project file, what a machine agrees to when it runs jobs for others, and how to hand over less.

Read it before you send a shared project file to someone outside your team, and before you start a runner on a customer's machine.

The short version

  • Whoever has the project file of a shared project can read and change everything in the project. There are no accounts, no roles and no read-only access.
  • Opening a project starts nothing. A machine runs a job for others only after its user said so, there: a tick in the app, or dbdb-cli runner or dbdb-cli schedule run started there.
  • A machine that runs jobs for others runs whatever jobs the project holds, as the user it runs as. Whoever has the project file can change those jobs. So they can read and write the files that user can, read and write the databases that machine reaches, and send what they read elsewhere.

Treat the project file of a shared project like an administrator password for every runner of that project.

What is in a project file

A project file is JSON that anyone can read without dbdb. Only the values of the vault are sealed.

In the file What a reader learns
The relay's address and the project's key (live) Enough to join: read the project as it is now, and change it. A relay's --password is part of the address
Connections of sources, database outputs and connectors Hosts, ports, database names, user names, and a password if one was typed in plain text
What each machine keeps for itself in a connector (Only this machine) The addresses every machine uses, by the machine's name. They are in the file so that other machines can see and copy them
env:NAME and the key variable of a connector The names of the variables that hold secrets on each machine, not their values
The vault The names of the secrets. The values are sealed, and whoever has the file can try passwords against them for as long as they like
Sources, jobs, queries, notes Tables and columns, SQL, file paths, and whatever was written into a note
Schedules and Push steps What the machines are called, and which job runs where and when

More than the file holds is kept in three places:

  • The sync folder and the relay keep the project's history. A password that was once typed into a connection is still there after it was moved to the vault, and in git if the file was committed.
  • A page in a browser keeps the project in the browser's storage, sealed with the project's key, which is in the file.
  • With direct connections on, every copy of the project is told the network addresses of your computer.

What someone with the file can do

On a machine that only has the project open

They can change or remove any source, job, schedule, connector, parameter and note, and the change shows there in about a second. They can stop the sharing for every copy that is connected. They see what the copy is called and which pane it works in.

They cannot start anything there. No job runs, no file arrives and no database is touched until the person at that machine does it, or agrees to one of the things below.

One thing to watch for: a job, a source or a connector that someone else changed looks like any other. Before you press Run on a shared project, look at what the job reads and where it writes.

On a machine that uses the Assistant or a Prompt step

A connector to a model is part of the project: its address, the name of the variable its key is read from, and its instructions. Someone who changes them changes where that machine sends the conversation, the rows a Prompt step sends, and the key.

  • The key variable can name any environment variable. With an address that was changed too, the value of that variable goes to another server as the key.
  • A key that is a secret of the vault goes to the connector's address whenever the vault is open.
  • The instructions go ahead of every conversation on every machine. The Assistant still asks before it changes the project or runs a job.

Only this machine does not guard against this: what a machine keeps for itself is in the project too, and whoever has the file can change it. On a project whose holders you do not all know, look at a connector's address and key in the Connectors pane before you use it, and start dbdb without variables that the project has no need of.

On a machine that runs jobs for others

A machine does this when one of these is true:

On the machine It runs
Run here ticked in the Job schedule pane Every schedule that names this machine
dbdb-cli schedule run project.json The same, from the project file
Run what is asked ticked in the Job schedule pane Any job another copy asks for, and it takes files pushed to it
dbdb-cli runner project.json All of it, unless --no-asked or --no-schedules says otherwise

Whoever has the project file can add a schedule that names the machine, change the job a schedule runs, or ask for any job with any parameter values. The run needs no further yes on the machine.

What a job can do there, as the user the runner runs as:

  • Read any file. A source reads the file at any path. A File or folder input reads a folder and all below it, with the content of every file.
  • Write any file. A File output, a File or folder output, an HTML output and an SQLite output write to any path, inside the project's folder or outside it, and make the folders that are missing. A file written into the right place, such as a shell's start-up file, a list of SSH keys or a service of the user, is run by the system later. So being able to write any file is being able to run commands.
  • Read any database the machine reaches, through a connection of the project or one written into a new source. Reads cannot change data.
  • Call any HTTP address the machine reaches, with a GET, through a REST API source, and read what it answers: an API, but also a web service on localhost or in the machine's network, and the metadata address of a cloud machine, which hands out that machine's credentials. A REST source sends nothing but a GET, unless the machine itself lists a host in DBDB_REST_POST: a POST can change things at an API, so leave that variable unset on a machine that runs jobs for others, or name only hosts that read with a POST. Set DBDB_REST_HOSTS to limit the hosts (see below).
  • Write to tables that exist, with the rights of the connection's user: add rows, update them, or replace all rows, which empties the table first. A job cannot change a table's structure or run SQL of its own.
  • Use the machine's secrets. A connection that reads env:NAME, or a secret of the vault while it is open there (DBDB_VAULT_PASSWORD), works for every job, also one that was added a minute ago. A secret written into a connection to another host is sent to that host. The key of a connector to a REST API is the same: its key variable can name any environment variable, and with an address that was changed too, the value of that variable goes to another host as the key.
  • Send what it read elsewhere: into a database on any host, to another machine with a Push step, or to a model.

A job cannot start a program. dbdb has no step that runs a command, and the only programs it starts itself are the Claude Code and Copilot CLIs of the Assistant, which it finds on the machine and never through the project.

A file that is pushed to a machine goes into Incoming beside its project file and nowhere else.

The ticks in the app

Run here and Run what is asked are kept by the app, for the project's file, and hold after the app was closed. Nothing in a project file, and nothing another copy sends, can set them: only someone at that machine can.

  • When a project with a tick is opened, a window says that this machine runs its jobs for others, and which: Keep running or Stop running here. The jobs run meanwhile, so that a machine left to run a night's schedules does not wait for a click.
  • A tick stands for the project it was given for. When the project in the file was shared with a new key since, is shared for the first time, is no longer shared, or is another project saved over the file, nothing runs for others until you say so again in that window: Run for others again or Stop running here. The same happens while the project is open, when another copy shares it anew. The people who hold the new key need not be the ones you said yes for.
  • A tick from a dbdb before this is asked about once.

dbdb-cli runner and dbdb-cli schedule run have no tick: starting the command is the yes, for as long as it runs.

Machines are known by name only

A machine is what its computer is called, or what DBDB_MACHINE says. Anyone with the project file can start a runner under any name. A file pushed to a machine goes to the runner of that name that came to the relay first, and a run asked of it can be taken by such a runner. Do not push data to a machine name on a project whose file may be in hands you do not know.

Taking access back

There is no way to take the file back, and less of a way to take access back than one would wish:

  • Stop sharing takes the address and the key out of every copy that is connected. Whoever still has a file with the old key can read what the relay kept until then.
  • A copy or a runner that was not connected at that moment still has the old address and key, and whoever has them can still change the project as that copy sees it. Give every runner the new file and start it again.
  • dbdb-cli runner follows a relay address and key that another copy changes, without asking. The app asks once for each new address, and stops running for others when the key changes, until you say so again (The ticks in the app).
  • Changing the vault's password does not close old copies of the file, which open with the old password.

To go on without someone:

  1. Stop sharing, then share again, which makes a new key.
  2. Send the new file to those who stay, and start every runner again with it.
  3. Change, at the database or the provider, every password and key that the project or its history ever held in plain text, and every secret of the vault if they knew its password.
  4. If the relay has a --password, change that too: it was in the file.

How to hand over less

When you send a file

  • Send it the way you would send a password, and keep it out of a repository that others read.
  • For someone who should look and not join, use Save a copy without the key…. The copy still names hosts, users, tables and machines: read it before you send it.
  • Keep passwords out of connections. Use env:NAME for what differs by machine and the vault for what is shared, and give the vault's password to fewer people than the file.

When you set up a runner, above all on a machine that is not yours

  • Give it a user of its own, which owns the project's folder and the folders the jobs read and write, and nothing else: no SSH keys, no sudo, no home folder that matters. What that user cannot read or write, no job can. With systemd:

    [Service]
User=dbdb-runner
ExecStart=/usr/local/bin/dbdb-cli runner /srv/etl/project.json
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
ReadWritePaths=/srv/etl

    This is a service of the system, not of a user as in remote-runs.md. It was not tried here.

  • Give it a database user of its own, with read on what the jobs read and write on the tables they fill, and no more.

  • Say which hosts it may call over HTTP. With DBDB_REST_HOSTS=api.example.com,*.corp.example set, a REST API source there calls those hosts and no other. Without it, any host. A runner that reads no API can be given a host that does not exist.

  • Give it only the variables its jobs read. Leave DBDB_VAULT_PASSWORD out unless a job there needs a secret of the vault.

  • Let it do only what it is for. --no-asked runs this machine's schedules and takes no asks and no files. --no-schedules does the opposite. --no-relay follows only the sync folder, so only those who reach that folder can change what runs.

  • Where nobody else should change what runs, do not share that project at all: keep a copy of the project file on the machine, set "no_sync": true or run dbdb-cli schedule run on it, and carry changes over by hand after you read them.

  • In the app, tick Run here and Run what is asked only for a project whose every holder you would let work at that machine, and untick them when the work is done.

When you run a relay

  • Give it a --password, so that only copies of your projects use it. The relay cannot read a project either way.
  • --forget-after-days keeps old projects, and with them old keys, from staying readable for good.

What dbdb does not have

So that nobody counts on it:

  • no accounts, roles, or read-only members of a shared project;
  • no limit on the folders or databases a job may use on a runner (the hosts a REST API source may call are the one exception, and only where DBDB_REST_HOSTS is set);
  • no list of jobs a runner may run, and no approval of a changed job before it runs;
  • no proof of which machine is which, and no record of who changed a job;
  • no way to make a copy of the file that was sent stop working.
