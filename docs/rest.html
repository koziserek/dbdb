REST API and OData sources

Sources that read a REST API or an OData service.

A REST API source reads the rows an API answers with. It asks with GET, reads JSON, and follows the API's pages to the last one. From there on the rows are like any others: a job filters, joins and writes them, and the app shows them as a table.

{"name": "orders", "source": {
  "kind": "rest",
  "url": "${connection:shop}",
  "path": "/orders?state=open",
  "rows": "data.items",
  "paging": {"kind": "next_link", "at": "links.next"}}}

In the app: Add source, type REST API.

An API that speaks OData is read with less to say: see OData services below.

Where the API is

url is the API's address, such as https://api.example.com/v1, or a connector to a REST API as ${connection:name}. Use a connector when the API wants a key, or when several sources read one API: the connector holds the address once and says where the key is. env:NAME takes the address from a variable of each machine.

path is what follows the address: /orders?state=open. It may name parameters, so one source reads ${day}'s orders.

Where the rows are

rows is the way to the rows inside an answer: the names to follow, with dots between them. For this answer it is data.items:

{"data": {"items": [{"id": 1, "customer": {"name": "Ann"}}], "total": 1}}

Leave it empty when the answer itself is the list of rows. An object where the rows should be is one row.

  • Columns are the fields of the rows, in the order first seen. A row that lacks a field has it empty.
  • An object inside a row is opened into columns of its own: customer.name beside customer.id.
  • A list inside a row stays as JSON text, in one column.
  • Values are text, as everywhere in dbdb. null and "" are both empty.
  • A number with more than 15 digits may lose its last ones: JSON numbers pass through a floating-point number. An API that gives such numbers as text keeps them whole.

Pages

APIs give pages in different ways. paging says which:

paging How the next page is asked for Reading ends
left out, or {"kind": "none"} It is not: one answer has every row after it
{"kind": "next_link", "at": "links.next"} At the address the answer gives at at, whole or relative when there is none
{"kind": "link_header"} At the address the Link header gives as rel="next" when there is none
{"kind": "offset", "parameter": "offset"} With offset set to the rows read so far at an empty page
{"kind": "page", "parameter": "page"} With page one higher; "first": 0 for an API that counts from 0 at an empty page
{"kind": "cursor", "at": "meta.next", "parameter": "after"} With after set to the mark the answer gives at at when there is none

offset and page also take "size_parameter": "limit", "size": 100. dbdb then sets limit=100 itself, and a page with fewer than 100 rows is the last, which saves the empty page at the end.

An API that names the same page a second time, or gives the same rows for two pages in a row, stops the read with an error. Otherwise a wrong setting would have a run go round for ever.

An API that answers 429 or 503 is asked again, after the time its Retry-After says, up to five times.

The key

A key is set up in a connector to a REST API, never in a source:

  • Key variable: the name of an environment variable. Each machine reads its own key from it.
  • Key secret: or the name of a secret in the project's vault, for one key that everyone with the vault's password uses.
  • Key sent as: bearer (the usual, and what an empty setting means) sends Authorization: Bearer <key>. basic is for a key that is user:password. Any other text is the name of the header the key goes in, such as X-API-Key.

A user and password in the address, https://user:${vault:name}@host, are sent as Basic too.

Signing in with OAuth

An API that wants a token from a sign-in server, as most business services in a cloud do, is set up in the same three settings:

  • Key sent as: oauth, then the address that gives the token, then the scopes to ask for, if any: oauth https://login.example.com/oauth2/token orders.read.
  • Key variable or Key secret: the client's id and its secret, with a colon between them: my-client-id:my-client-secret.

Before a read, dbdb asks that address for a token and sends the token to the API as Authorization: Bearer. This is the sign-in of a program (OAuth 2.0, the client credentials grant), which needs nobody at a browser, so a job on a runner signs in the same way. What holds for it:

  • The id and the secret go to the address that gives the token and nowhere else, never over http:// except to this machine, and only to a host DBDB_REST_HOSTS allows, where that is set. The API itself gets only the token.
  • A token is asked for at the start of each read and kept nowhere: not in the project, not on disk, and not in what a test shows.
  • A read that takes longer than the token is valid stops with the API's refusal. It is not signed in again in the middle.
  • When the sign-in is refused, the error says what the server said, such as invalid_client, and nothing of the secret.

A sign-in where a person agrees in a browser (the authorization code grant) is not built, since the token it gives belongs to that person and would have to be kept for them somewhere. A token from such a flow still works as a bearer key for as long as it is valid.

What a REST source will not do

These hold for every REST source, so that a project file from someone else cannot turn a read into something else:

  • A GET, unless the machine allows a POST. A read never changes what it reads, so a source asks with a GET and sends nothing along. A source that names something to send asks with a POST, and dbdb sends one only to the hosts the machine lists in DBDB_REST_POST (below). No other method is ever sent. The sign-in of a connector that is set up for OAuth is a POST too, to the address that gives its token.
  • The key goes to one host. A next page or a redirect on another host stops the read, with an error that names the host, instead of carrying the key there.
  • No key in plain text. A key is not sent over http://, except to this machine itself (localhost).
  • Only the hosts a machine allows. Where DBDB_REST_HOSTS is set, dbdb calls no other host: DBDB_REST_HOSTS=api.example.com,*.corp.example. Set it on a machine that runs jobs for others (sharing-and-trust.md).

An API that searches with a POST

Some APIs read with a POST: the search of a document store, a report that takes its filter as JSON, GraphQL. For these a REST source has Sends: the JSON to send along. With something in it, the call is a POST with Content-Type: application/json; empty, it is a GET.

dbdb cannot see whether a POST only reads. The same address could as well add an order. So this is the one thing a project file cannot switch on by itself:

  • A POST goes only to the hosts the machine lists in the variable DBDB_REST_POST, written like DBDB_REST_HOSTS: DBDB_REST_POST=search.example.com,*.corp.example. Where it is not set, no source sends a POST, and the error names the variable and the host. Set it on your machine, and on a runner, for the APIs you know to only read with it.
  • What is sent has to be JSON, and it is sent as written. No parameter is filled into it.
  • The pages follow in the address, as for a GET, and every page is sent the same. An API that wants the page inside what is sent is read for its first page only: set Pages to none.
  • A redirect in answer to a POST is not followed.
  • Every other limit above holds as for a GET.

The API Call Builder shows POST and what is sent under Asks before anything is asked, and Copy as curl writes it with -d.

In a project file it is "body", a text: "body": "{\"query\": \"open\"}".

Large answers, and the browser

Every page is read before the first row is given, so that the columns are those of all rows. What was read is held in memory; a source of millions of rows is better copied once into a database or a Parquet file by a job. A preview in the app stops after the page that fills it.

A page in a browser can only read an API that allows calls from the page's address (CORS). Most APIs do not, so REST sources are for the desktop app and dbdb-cli in practice.

OData services

OData is a standard for REST APIs, which SAP, Microsoft Dynamics, SharePoint and many others speak. It settles what a REST source has to be told: where the rows are, and how the pages follow. So an OData source names only the service, the entity set (OData's word for a table) and, if wanted, what the service should filter:

{"name": "orders", "source": {
  "kind": "odata",
  "url": "${connection:erp}",
  "set": "Orders",
  "query": "$filter=Year eq 2026&$select=ID,Customer,Total"}}

In the app: Add source, type OData service. Look up lists the service's entity sets.

  • url is the service's address, the one that $metadata follows, such as https://erp.example.com/odata/v4, or a connector to an OData service as ${connection:name}. The connector has the settings of a connector to a REST API, the key among them.
  • set is the entity set.
  • query is OData's query options, which the service itself applies: $filter, $select, $orderby, $expand, $top. Left out, every row is read. It may name parameters.

Versions 2 and 4 are read, and version 3 where it answers like one of them. The source does not say which: it shows in the answer. The answer has to be JSON, which dbdb asks for; a service that answers only in Atom (XML) is not read.

The rows are as a REST source's, with three differences:

  • What the service says about a row and not in it is left out: @odata.etag and its like, __metadata, and version 2's links to rows that were not asked for.
  • A date of version 2, /Date(1767225600000)/, is written out as 2026-01-01 00:00:00.
  • A row that $expand brought along is opened into columns like any object in a row; a list of them stays JSON text, unless the source says each.

A row for each related row

$expand puts related rows into each row. Where a row has one related row, such as the customer of an order, its columns stand beside the row's own: Customer.Name. Where it has many, such as the lines of an order, they come as a list. each names one such list, and the source then gives a row for each related row in it:

{"name": "order lines", "source": {
  "kind": "odata",
  "url": "${connection:erp}",
  "set": "Orders",
  "query": "$expand=Lines",
  "each": "Lines"}}

An order with three lines is three rows, each with the order's columns and one line's as Lines.No, Lines.Qty. An order without lines is one row with those columns empty, so no order is lost. It is what a Join step of two sources would give with every main row kept, read in one go.

  • One list can be rows. Another list that is brought along stays JSON text in a cell.
  • The query has to bring the list along ($expand=Lines), or the read stops and says so.
  • Only some columns of the related rows are asked for as the service's version writes it: $expand=Lines($select=No,Qty) in version 4, and $select=*,Lines/No,Lines/Qty&$expand=Lines in versions 2 and 3.
  • A project file with each is written as "format": 8, so that an older dbdb says a newer one is needed.

Reading only what changed

A job that copies a large entity set every night reads every row every night. An OData source can say that a run reads only what is new since the run before, in one of two ways.

Newer by a column. The source names a column that only grows: a date of the last change, or a number the service counts up.

{"name": "orders", "source": {
  "kind": "odata",
  "url": "${connection:erp}",
  "set": "Orders",
  "changes": {"newer_by": "ChangedAt"}}}

Before a run reads, it asks the service for the largest value the column has now. It then reads the rows whose value is larger than the largest of the run before ($filter=ChangedAt gt …, added to the source's own filter), and when the run has ended well, the new largest value is kept for the next run. The first run reads every row.

  • The value is asked for before the rows are read, and is not taken from them. A row that is written while the run reads is read again by the next run, and none is missed.
  • A row that is deleted at the service is not noticed, and a row whose column is empty is read by the first run only.
  • A run asks the service for its $metadata first, to write the value as the column's type wants it.

The service's own changes. A service of version 4 that follows its changes ends an answer with a delta link when it is asked to (Prefer: odata.track-changes), and gives behind that link what has changed since.

{"name": "orders", "source": {
  "kind": "odata",
  "url": "${connection:erp}",
  "set": "Orders",
  "changes": "delta"}}

The first run reads every row and keeps the link. Each run after it reads from the link of the run before: the rows that are new or changed, and the rows that are gone. A source that reads this way always has two more columns, @removed and @id. They are empty for a row that is there. For one that is gone, @removed says why (deleted, or changed for a row that still exists and is no longer among those the query asks for) and @id what the service calls it, with the key columns where the service gives them. A Filter step on @removed sends them where they belong.

  • A service that gives no delta link is read whole by every run. dbdb-cli changes says so.
  • A link that the service no longer knows makes the run fail with the service's answer. Begin again as below.

For both ways:

  • What is remembered is in odata-changes.json beside the project file: for each source, service and entity set the largest value or the delta link, the query it is of and when it was read. It holds no key. It is this machine's own and not part of the project: another machine that runs the job begins with every row, and so does another environment, which reads another service.
  • It is kept only by a run that wrote and did not fail. A dry run reads what a run would and keeps nothing. After a run that failed, the next one reads the same rows again.
  • Every row is read again when the source's query, entity set or column changes, since what was remembered is of another call.
  • A run with nothing new gives the steps after the source no rows, with the columns of the last run that had rows, so that a step that names a column still finds it. The columns are remembered in the same file.
  • A preview and a test read every row, whatever is remembered, and so does a run of a project that is not saved, or in a browser, where there is no file to remember in.
  • To begin again: dbdb-cli run-job project.json job --from-start, dbdb-cli changes project.json --forget orders, or Read every row next time in the API Call Builder.
dbdb-cli changes project.json

lists what is remembered, one source a line.

What the job writes to is yours to choose with this in mind: a run now brings only some rows, so an output that replaces a file holds only those. A database output that adds or updates rows is what such a source is usually wired to (database-output.md).

  • A project file with changes is written as "format": 8.

Everything under "What a REST source will not do" holds for an OData source too.

A service also says what it holds, in its $metadata: the entity sets, their columns, their keys, and what leads from one entity set to another, its navigation properties. The Graph pane draws it: pick Service of and a source that reads the service, and every entity set is a table and every navigation property a line (see below for which column a line starts at). Look up and a connector's Test connection read it too, and so does

dbdb-cli export-keys project.json --database orders --whole -o erp.keys.json

which writes what the service that the source orders reads says it holds, with its keys, as a key file, as it does for a database.

A navigation property says that rows are linked, and not always by which columns. dbdb makes of each one of three things:

  • A foreign key, where the service names the columns (a referential constraint).
  • A foreign key, where it names none and the names tell: the entity has a column with the name of the one key column of the entity the property leads to. Orders.Customer leads to Customers, whose key is CustomerID, and Orders has a CustomerID. The key's comment says that it was made this way. None is made of a key that is the entity's own whole key (every entity's ID), of an entity to itself, between two entities that lead to many of each other, or where two properties lead to the same entity.
  • A line of the Graph and no key, where neither says the columns. The property is a row marked nav under its table's columns. It can be followed with $expand; it cannot be joined on, and a key file does not hold it.

A property and the one that leads back are one link.

Not built: writing to a service, $batch, and asking the service for its count of rows.

Building and testing a call in the app

The API Call Builder pane is where a REST or an OData source is worked out when its settings are not in hand yet. Open it from Add pane, from a source's menu in the Sources pane (Open in API Call Builder), from the source dialog (Build and test…, which goes on with what was typed there), or from a connector to an API in the Connectors pane (Build a call…).

  • On the left are the project's API sources, under the connector each reads through. + beside a connector starts a new call through it.
  • The form has the settings of the source dialog. Under it, Asks shows the first page's address as it will be asked for, and follows what is typed. Nothing is asked until Test. Copy as curl copies the call as a command for a terminal. A key is not in it: the command has <key> where one goes.
  • Test asks the API as a job would, through the same reading, so every limit under "What a REST source will not do" holds for it. It stops after the page that reaches 200 rows.
  • Rows shows the rows a job would get. Pages lists each page that was asked: its status, how long it took, how many rows came of it and how long the answer was. A page opens to what was asked, with the name of the header the key went in and never the key, and to the answer as a tree.
  • For a REST API, a list in the answer has the button Rows are here, which writes its place into Rows at.
  • A test that fails keeps the pages up to the one that stopped it, with what the API answered there.
  • Add source or Update source keeps the call as a source of the project. It is a rest or an odata source like any other, and Undo takes the change back. Revert gives up what was typed.

The pane holds no key: a key is a connector's.

What a REST API's first answer suggests

A REST API does not say where its rows are or how its pages follow. Both can often be seen in its first answer. After a Test of a call that does not say where the rows are, found none, or has no paging, the pane says what it sees there, for example:

The first answer suggests: the rows are at products; pages: A parameter skips rows (offset).

Take it fills that into the form, and the next test shows whether it is right. The reasons are shown when the mouse is over the button. What is looked for:

  • the list of objects nearest the top of the answer, and of those the longest;
  • the address of the next page, in the Link header or in a field such as next or _links.next.href;
  • a mark for the next page, such as next_cursor. The name of the parameter it is sent back as is a guess to check against the API's documentation;
  • a count of rows skipped (offset, skip) or a page number, in the answer or in the address that was asked.

It is a proposal. Nothing changes until it is taken, and an API that shows none of this gets none.

Starting from a curl command

The documentation of an API mostly shows a call as a curl command. New call, From a curl command… opens a box to paste one into, and Fill the form takes its address and its path.

  • Only a GET is taken. A command that sends anything else, or sends something along (-d, --json, -F), is refused and the reason said. For an API that searches with a POST, write what it sends into Sends yourself (below).
  • The key of the command is not kept, and is in no setting afterwards. The pane says how it travels, and Make a connector for it adds a connector to the API's address, through which the call then reads. The key is given to that connector in the Connectors pane, as the name of a variable or a secret of the vault. When a connector to the same address is there already, the call goes through it.
  • A parameter in the address that is named like a key (api_key, token) is taken out and named, since the path is written into the project file. A key travels in a header, from a connector.
  • Headers a source does not send, and a cookie, are named as left out.

Starting from an OpenAPI file

Many APIs describe themselves in an OpenAPI file (Swagger, in its version 2). New call, From an OpenAPI file… asks for one: a file in JSON or YAML, or the address of one such as https://api.example.com/openapi.json. List its calls reads it, and the calls it describes are listed on the left, with a search when there are many. What each is for and the parameters it takes show when the mouse is over it.

A click on one starts a call with what the file says of it:

  • the API's address, or the connector that has this address;
  • the path, with the parameters the call cannot be asked without, each still to be given a value. A name in braces in the path, such as {id}, is to be filled in;
  • where the rows are, when the file describes the answer and a list of objects is in it;
  • how the pages follow, when a parameter is named for it (skip, offset, page).

While the file is listed, a call whose path is one of its calls has a field for each thing the call takes, under What the call takes: the ones it cannot be asked without are marked with a star. What is typed there is written into the path, and what is typed into the path shows in the fields.

When the file says the API takes a key, the pane says how it travels and offers to make a connector for it, as for a curl command.

Only calls that are a GET are listed, which is what a source reads with. The file may be in JSON or in YAML. An address is asked for the file with a GET and without a key. The file is the API's maker's description, so the call is a start, to be tested like any other.

Clicking an OData call together

An OData service says what it holds, so its call need not be typed. Look up beside Entity set asks the service for its $metadata. After that:

  • The service's entity sets are listed on the left, each with how many columns it has and its key when the mouse is over it. A click picks one for the call.
  • Under Query options the same options are shown as parts:
    • Columns: tick the columns to read ($select). None ticked reads every column.
    • Conditions: rows of a column, a comparison and a value ($filter). Every row must hold. A text column can also be asked whether it contains, starts with or ends with a text, and any column whether it is empty. one of takes several values with commas between them, and holds when the column is any of them.
    • Order: the columns to order by, smallest or largest first ($orderby).
    • Limit: the most rows the service is to give ($top).
    • Bring along: related rows the service is to put into each row ($expand), by the names the service gives the ways to them. For each that is ticked, a menu picks the columns of the related rows to ask for, and where the way leads to many rows, A row for each of … makes them rows of their own (above).

A run reads, under the query options, says which rows a run of a job reads: every row, only the rows newer by a column, or only what the service says has changed (above). Below it the pane says where the run before left off, and Read every row next time takes that away.

After a test, the same ways stand above its rows as Related rows, each a button: a click brings those rows along and tests again, so the related columns are there to look at. A way to many rows is made rows of its own by that click, unless another list is already.

The text in Query options stays what the source holds. A click changes the text, and a text that is typed or was written by hand is read into the parts, so both can be used on the same call.

A value is typed as it reads, Switzerland or 2026-01-31, and is written as the column's type and the service's version want it: 'Switzerland', and datetime'2026-01-31T00:00:00' for a service of version 2 or 2026-01-31T00:00:00Z for one of version 4. contains is written as substringof for version 2.

A filter that is more than conditions joined by and, one with an or between different columns, other brackets or a function, is not shown as rows. It stays as it is written and is sent as written. An option that is none of the five, such as $count=true, is kept as well.

Count, beside Test, asks the service how many rows the filter leaves (Orders/$count?$filter=…) before any row is read. The number is of the call as it was asked, and goes when the call changes.

A service that was looked up stays known while the pane is open, so another call to it has its entity sets and parts at once.

A service of version 2 or 3 gives related rows only when they are among the columns asked for, so with columns ticked the pane adds what is brought along to $select itself.

A filter the service could run

A job that filters an OData source right after reading it reads every row first and drops most of them. When the pane is on such a source, it says so, for example:

The job export filters these rows right after reading them (Country = Switzerland; Total ≥ 10). The service could do that itself, so that fewer rows travel.

Add to the query adds those conditions to the query options. It is a change of the call like any other: test it, then Update source. The Filter step stays where it is, so the job gives the rows it gave, and only fewer of them travel.

The same goes for columns. When the step after the source, or after its Filter step, is a Map step that only copies columns and sets fixed values, the pane names the columns the job goes on with, and Add to the query asks the service for only those ($select). The columns the Filter step looks at are among them. A Map step that works a value out with an expression is left alone, since what it reads is not looked into.

In the Designer, the settings of such a step say the same in one line, with Open its call, which shows the source in this pane. The line goes once the source's query does what the step does.

Nothing is moved unasked, and the note is careful about what it offers:

  • Only conditions under which the service gives at least every row the step keeps: a value or one of several values a column must equal, and numbers a column must lie between or must not be. A text search and a comparison of texts are left to the step, since services differ in how they compare texts.
  • Only when the Filter step is the one place the rows go, its rejected rows go nowhere, and nothing else in the project reads the source: the query changes the rows for every reader.

Where a step's work is done

In a job that reads an OData service, each step that follows the source carries a mark in its header in the Designer, for as long as the rows go to one place:

Mark What it says
at the service The source's query asks the service for it. The step that reads the source always has this mark. A Filter or Map step has it when the query does all the service can do of it. The step still runs, on what arrives, as a check
partly at the service The query does some of a Filter step, and the rest is done by dbdb
the service could dbdb does it, and the source's call offers to add it to the query
here dbdb does it, on the rows the service sent

The mouse over the step, and the step's settings, say the same as a sentence with the reason, such as what the service is asked for, or that a text search is left to the step. Open its call in the settings shows the source in the API Call Builder.

The marks only tell. What decides is the query of the source, and a step is never taken out of the job: one whose work the service does keeps running, so the job gives the rows it gave whatever the service makes of the query.

A Sort step is always done here. The same rows would travel in any order, so nothing is saved by asking the service to sort, and a service may order texts another way. A job has no step that keeps only the first rows, so there is nothing of a limit to leave to the service either; $top in the call stays a setting of the source.

dbdb-cli show project.json and the assistant's summary of a project say the same under each such step.

In a browser the form and the address work, and a test reaches only an API that allows calls from the page's address, as a source does.

From the command line

dbdb-cli preview https://api.example.com/v1/orders --table data.items

reads one answer and shows its rows; --table is where the rows are. A source with paging or a connector, and an OData source, is part of a project: dbdb-cli preview project.json --source orders.
