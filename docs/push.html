Pushing a file to another machine

A job that sends its result to another machine.

A job can hand its result to another machine that has the same project. The step Push to another dbdb writes its rows as a file, as a File output does, and sends the file to the machine it names. There it is saved in the folder Incoming beside the project file, and a job of that machine reads it as any file.

Use it when one machine can read the data and another has to have it: a laptop inside a network reads a database and pushes the rows to a server outside it, or the other way round.

The step

{"type": "push", "machine": "etl-box", "name": "customers.csv", "format": {"kind": "csv"}}
  • machine: what the other machine is called. That is the computer's name, or what DBDB_MACHINE says there, as for schedules and runs on another machine. Capital letters do not matter.
  • name: what the file is called there. It is a name and never a path: what is pushed goes into Incoming and nowhere else, so nothing that another machine sends can reach the project file or anything beside it. A name may hold a parameter, as customers-${day}.csv.
  • format: as for a File output (write): CSV, JSON, Excel, Parquet or an SQLite file. CSV unless said.

The step has the rejected port of a File output, and the project's checks decide what goes there.

In the Job designer it is Push to another dbdb among the steps. Its settings list the machines that are listening now.

What happens in a run

  1. Before a row is read, the run looks whether the other machine is there. If it is not, the run stops and says what to start there.
  2. The rows are written to a file on this machine, in the folder for temporary files (DBDB_TEMP_DIR).
  3. When the input has ended, the whole file is sent. On the other machine it is written beside its place and takes the place of a file of the same name only when all of it has arrived and is what was sent. Whoever reads Incoming there sees the old file or the new one, never half of one.
  4. The file on this machine is removed.

A dry run and validate check the rows and send nothing. They do not need the other machine.

Not later. The other machine has to be there when the job runs. A file is not kept to be sent when the machine comes back: the run fails, and its record says why. Run the job again.

The machine that takes the file

A machine takes what is pushed to it only after its user said so, there, for that project. It is the same word as for runs on another machine (remote-runs.md): a machine that runs what other copies ask of it also takes their files.

  • dbdb-cli runner project.json takes them, and writes a line for each file that arrived. With --no-asked it takes none.
  • The app takes them while the project is open there and Run what is asked is ticked in the Job schedule pane. The status bar says what arrived.

To read what arrives, add a source there with the path Incoming/customers.csv, as for any file.

Whoever has the project file can push to such a machine, into that one folder. That is less than they could do already: they could ask the machine to run a job that writes any file.

How the file travels

The first of these that is there:

  1. To this machine itself, when machine is its own name: the file is written into Incoming beside the project file. This is how to try a job out.
  2. Through the project's folder, when a runner on the other machine says in the sync folder that it is here. The two machines then reach the same project folder, and the file is written into its Incoming.
  3. Through the relay of a project that is shared through one (shared-projects.md). The file goes in pieces of 256 KB, each sealed with the project's key, to the one copy that takes it. The relay hands each piece on and keeps nothing: the file is never in the project's room, never in what the copies sync, and the relay cannot read it. The sender waits for the other machine to say it has a piece before it sends the next.

The file is never in the project file and never in what the copies sync. Only the step is.

The relay has to be the dbdb-cli relay of this version or a later one. An older relay does not hand files on, and the run says so.

Copies that are connected directly (shared-projects.md) still push through the relay. Sending the file over the direct connection is not built yet.

A page in a browser

A page cannot push a file, and takes none: it has no folder to keep a file in, and a job that writes does not run in a page. Have a machine run the job: Run on… in the Job designer. The page can build the job, check it with a dry run, and ask.

From the command line and an assistant

dbdb-cli run-job project.json send pushes like a run in the app, and so do schedules and the run_job tool. No copy of the project has to be open on the sending machine: for a relay, the command goes to it for the time of the push only.

Limits

  • One file for each Push step, and one machine. To send to two machines, use two steps.
  • A project that is not shared through a relay pushes only to itself and to machines that reach its folder.
  • Nothing tells the other machine to run a job when a file has arrived. Schedule the job there (schedule.md), or ask for it with Run on… after the push.
  • A push that is stopped half way leaves nothing on the other machine. One that the other machine's power cut stops can leave a file whose name begins with a dot and ends in .part in Incoming. It can be deleted.
  • With two runners on machines of one name, the file goes to the one that came to the relay first.
  • It was tried with a relay and both machines on one computer, not across the internet.
  • A project with a Push step is written as "format": 5, so a dbdb from before the step says that a newer one is needed.
