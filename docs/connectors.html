Connectors

Models, servers and services a project reaches, set up once and named.

A connector is what a project reaches outside itself, set up once and named:

  • a connector to a model is who answers in the Assistant and in a job's Prompt steps;
  • a connector to a database holds the connection that sources and database outputs read and write through;
  • a connector to a REST API holds the API's address and says where its key is, for the sources that read it.

The Connectors pane (🔌) lists them and shows the chosen one as a form. Connectors are part of the project file, so every copy that opens the project, here or through a sync folder, a relay or a browser, has the same ones. Every change is a command: Undo takes it back, and dbdb-cli apply and the MCP tools do the same.

For everybody, or for this machine

Each setting of a connector is everybody's until a machine keeps its own. Tick Only this machine beside a setting, and what you type there is for this machine alone: the other machines keep what they have. Untick it to take everybody's again.

So one connector works where the machines differ. A database that the office reaches at db.internal and a laptop through a tunnel on localhost:5433 is one connector with two connections, and every source that reads through it works on both. A llama-server on each desk is one connector with an address for each.

A connector as a whole is for every machine that opens the project. Tick The whole connector is only for this machine and the other machines are no longer offered it; another machine that ticks it too joins this one. Where a connector is only for other machines, the form says which, with This machine too and Every machine. A connector to a database is also not for a machine where it has no connection. One that is not for this machine is listed greyed out and is not offered: the Assistant does not ask through it, and a source that reads through it says that no connector of that name is for this machine.

Other machines lists the other machines the connector names, each with what it keeps for itself. Copy to this machine gives this machine the settings that machine uses, as its own, and makes the connector one for this machine too. The other machine keeps what it has, and what you change afterwards is this machine's alone.

What a machine keeps for itself is in the project like the rest: that is how another machine can see it and copy it. It is no place for a secret (see below).

A machine is known by its computer's name, the one the pane shows as This machine. dbdb-app and dbdb-cli on one computer are the same machine. Set DBDB_MACHINE before starting dbdb to call a machine something else. A browser has no name for the computer, so the pane asks for one there and the browser keeps it. Capitals do not tell machines apart. The machines say where a connector works. They are no lock: whoever has the project file can change them.

A connector to a model

  • a name, which is what the Assistant's header lists;
  • a kind: Ollama, llama.cpp, Claude, Claude Code or Copilot (assistant.md says what each needs);
  • an address (Ollama, llama.cpp) and a model. Another model chosen in the Assistant's header is that copy's own choice and does not change the connector;
  • a key variable (Claude, llama.cpp): the name of an environment variable, such as TEAM_CLAUDE_KEY. Each machine reads its own key from it. A key itself is never kept in a connector: dbdb refuses anything that is not the name of a variable, so no key reaches the project file or another machine. Left empty, Claude reads ANTHROPIC_API_KEY;
  • or a key secret in its place: the name of a secret in the project's vault, for one key that everyone with the vault's password uses. The key is in the project sealed, and the Assistant asks for the vault to be unlocked before it starts;
  • a key for this run: a key typed into the pane, for this machine, kept until dbdb closes and never saved. It goes before the variable and the secret;
  • instructions, sent ahead of every conversation after dbdb's own: the language to answer in, what the tables are about, what to leave alone. They add to how the assistant answers; what it may read and change stays as assistant.md says.

Claude Code and Copilot connectors are not offered in a browser, which cannot start a program. When no connector to a model is for this machine, nobody answers there, and the Assistant says so.

The Assistant itself holds no address, model list or key any more. What a copy of dbdb was set up with before connectors (an Ollama address, a model) answers nobody by itself: Add connector fills a new connector of that kind in with it, so it is one click to move it into the project.

A connector to a database

  • a name;
  • a kind: PostgreSQL, SQL Server, MariaDB / MySQL, Oracle, SQLite or MS Access;
  • the connection, written as in a source: a connection string, env:NAME for one that a variable of each machine holds, or the file of an SQLite or Access database.

A source or a database output reads through it when its connection is ${connection:name}. In the app, choose it under From a connector ⏷ below the connection of a source or of a database output. A project file says it the same way:

{"name": "orders", "source": {"kind": "postgres_table",
  "url": "${connection:warehouse}", "table": "public.orders"}}

The connection of a connector may name parameters, so test and production each have theirs, and takes its password from the vault as ${vault:name}. Do not write a password into it: the project file is shared, and the pane and validate say so when one is there. Move passwords to the vault in Edit > Vault… (or dbdb-cli vault move-in) seals it and writes the secret's name in its place, for everybody's connection and for each machine's own.

A connector to a REST API or an OData service

  • a name;
  • the address of the API, such as https://api.example.com/v1. A source adds its own path to it;
  • a key variable or a key secret, as a connector to a model has them: the name of an environment variable that each machine reads its own key from, or the name of a secret in the project's vault. Never the key itself;
  • key sent as: bearer (also when left empty) for Authorization: Bearer <key>, basic for a key that is user:password, or the name of the header the key goes in, such as X-API-Key. oauth and the address that gives a token signs in first, with the client's id and secret as the key (rest.md).

A REST API source reads through it when its address is ${connection:name}: choose it under From a connector ⏷ in the source's settings.

{"name": "orders", "source": {"kind": "rest",
  "url": "${connection:shop}", "path": "/orders", "rows": "items"}}

The key goes to the host of the connector's address and to no other, only with a GET, and not over plain http:// except to this machine itself. rest.md says what else a REST source will not do.

Build a call… opens the API Call Builder with a new call through the connector.

A connector to an OData service has the same settings. Its address is the service's own, the one that $metadata follows, and an OData source reads through it.

Test connection tries the connector as this machine has it. A database is asked for its tables: nothing is read or changed. A model is asked for its models. A REST API is sent one GET to its address, with the key, and the pane says what it answered. An OData service is asked for its $metadata, and the pane says how many entity sets it has. For Claude only the key is looked for, since its API has nothing to ask that costs nothing; the key itself is tried with the first question.

Sources that hold their connection themselves keep working as they are. Add connector ⏷ > From the connection of a source makes a connector of such a connection and has every source and database output with the same connection read through it, in one step that one Undo takes back.

Renaming a connector takes what reads through it along. The pane says what reads through the one shown.

From the command line and for an assistant

dbdb-cli connectors project.json lists them, with the settings as this machine has them, and says which this machine may use; --machine NAME answers for another machine, --json prints them as data, and --usable NAME exits with status 1 unless that connector may be used here. Over MCP the tool is list_connectors. They change with the commands add_connector, update_connector, rename_connector and remove_connector (agents.md).

The project file

A project file with connectors is written as format 2, which a dbdb from before connectors does not open: it would save the file without them. One with a connector to a database, or with a setting that a machine keeps for itself, is written as format 6, and one with a connector to a REST API as format 7. A project without connectors stays in format 1 (shared-projects.md).
