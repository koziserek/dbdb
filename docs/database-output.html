Database output

Writing rows to PostgreSQL, SQL Server and SQLite tables.

A Database output step writes the rows it is given into a table of PostgreSQL, SQL Server or an SQLite file, and can give back the ids the database made for them.

{"type": "database",
 "db": {"kind": "postgres", "url": "${db}"},
 "table": "public.parts",
 "mode": "upsert",
 "keys": ["part_no"]}

db is {"kind": "postgres", "url": ...}, {"kind": "sql_server", "url": ...} or {"kind": "sqlite", "path": ...}, with the same connection strings as sources: env:NAME reads one from an environment variable, and ${name} takes a project parameter, so one job loads test and production.

What it does

  • On PostgreSQL and SQL Server the table must exist. An SQLite file or table that is not there yet is made by the run: the file, the folders it lies in, and a table with a column for each input column, typed as a File output to SQLite types them. For upsert the keys are the new table's primary key. A dry run makes nothing: it tests the rows against an empty table in memory. A table that is there is never changed.

  • Input columns go into the table's columns of the same name; use a Map step before the output to pick, rename and convert. Table columns the input does not have keep their default.

  • Values travel as text and the database converts them to each column's type, so 2026-01-31 goes into a date and 12.50 into a numeric. An empty value is NULL.

  • mode says what happens to the rows:

    Mode In the app Does
    insert add rows adds the rows to the table
    upsert update or add rows updates the row with the same keys, adds the others
    replace replace all rows empties the table, then adds the rows

  • For upsert, PostgreSQL and SQLite need a primary key or unique index on the key columns; SQL Server does not. The rows must have one row for each key: add a Remove duplicates step if they may not.

Loading only what changed

upsert is the mode for loading the same table again: a rehearsal run after the source moved on, or the delta load at cutover.

  • A row that is in the table with the same values already is left alone: it is not written again, so triggers and "last changed" columns of the table see only the rows that really changed. The values are compared in the database, after it has converted them, so 2.50 equals 2.5 in a numeric column. Table columns the input does not have are not compared and keep their value.
  • The run says what it did: wrote 1200 rows to public.parts, 0 issues, 3 added, 2 changed. A dry run says what it would do, which previews the delta before anything is written.
  • Nothing is saved between runs and the source needs no "modified" column: the table itself says what is new.

Rows that are gone from the source stay in the table unless the step asks for them to go:

{"type": "database", "db": ..., "table": "public.parts",
 "mode": "upsert", "keys": ["part_no"],
 "delete_missing": true}

With delete_missing (in the app: "Delete rows that are gone from the input", off unless ticked) the step, after writing, deletes every row of the table whose key columns match no input row. The table then holds the input's rows and nothing else, and the report adds 1 deleted (a dry run: delete 1). So that it deletes no more than is meant:

  • Give the output all the rows the table should hold. A Filter before it that passes only some of them makes the others count as gone.
  • A row that the checks reject (see below) is not gone: its row in the table stays as it was.
  • An input with no rows deletes nothing; the run stops with an error instead of emptying the table. Use replace when that is meant.
  • Table rows with an empty key column are never deleted.
  • Run Check outputs or --dry-run first and read the number.

On SQL Server, a table with xml, text, ntext, image, geography or geometry columns has every matching row written and counted as changed, because those types cannot be compared.

All or nothing, and a real dry run

The whole write is one transaction. If the database refuses a row (a value that does not fit its column, a missing mandatory value, a key that is there already) nothing is written and the error says what the database said.

Check outputs in the app, run-job --dry-run and the MCP server's default all go through the entire write and then take it back. A dry run that passes has put every row through the table's types and constraints.

Large loads: committing in parts

A load of millions of rows in one transaction makes the database carry all of it until the end: locks, and a transaction log that grows with every row. commit_every (in the app: "Commit every") commits after each that many rows instead:

{"type": "database", "db": ..., "table": "public.parts",
 "mode": "upsert", "keys": ["part_no"],
 "commit_every": 10000}

It is off unless set (0, shown as "all rows"), and it changes what a failure leaves behind:

  • The rows committed before the failure stay in the table. The error ends with how many: ...; the first 40000 rows are in table public.parts already, committed before this happened. A failure before the first commit keeps nothing, as without the setting.
  • An upsert can simply be run again: the rows that went in are left alone the second time. An insert cannot, because those rows would go in twice (or be refused as duplicates); take the rows already written out of the input first, or empty the table.
  • replace empties the table in the first part, so a failure leaves a table that is emptied and partly filled.
  • With delete_missing, the rows that are gone are deleted in the last part, after every row is written.
  • A dry run does not commit in parts: it still goes through every row in one transaction and takes it back. On a very large load that is the one huge transaction the setting avoids, so try the load on a test database rather than dry-running it against production.

Rows go to the server up to 5,000 at a time on PostgreSQL and up to 1,000 on SQL Server, and a commit falls between two such sends. A number up to those is kept exactly; a larger one commits at the first send that reaches it, so 12000 on PostgreSQL commits every 15,000 rows. In the browser build an SQLite file is written when the run ends, so there the setting changes nothing.

Memory

Run from the command line, an insert or replace into SQLite or PostgreSQL sends its rows to the database as the job produces them and holds none, so a load of any size needs the same memory. The step holds all its rows until its input ends, as every output did before, when:

  • the mode is upsert, which looks at every key before it writes;
  • something is wired to its written port, or it has returning columns;
  • another output of the job writes to the same database, so that the two write one after the other;
  • the database is SQL Server.

A PostgreSQL source of the same job is read in batches while the output writes, even into the table it reads: the rows read are those that were there when the job began. An SQLite source in the file the job writes to is read whole first, and so is an SQL Server source of the database the job writes to.

Rows the checks reject

Like the other outputs, the step has a rejected port. Wire it to a File output and the rows the project's rules find something wrong with go there instead of to the database.

New ids for the rows of other tables

When the table makes its own ids, the rows of other tables that point at it need the new id in place of the old key. Two settings give it to them:

{"type": "database",
 "db": {"kind": "postgres", "url": "${db}"},
 "table": "public.customers",
 "returning": ["id"],
 "pass_on": ["old_id"]}
  • returning ("Get back" in the app) names columns of the table to read back for each row written: an id the database generated, or anything else it fills in.
  • pass_on names input columns that are not written, only passed on: the old key, when the table has no column for it.

The step's written port gives the rows it wrote with both: here old_id, the written columns and id. Wire it to the lookup input of a Join on the old key, and the orders get the id of their customer; or to a File output, to keep the list of old and new keys.

customers ─▶ Database output (customers) ─written─▶ Join ─▶ Map ─▶ Database output (orders)
orders ───────────────────────────────────────────▶ (main)
  • The parent table is written first, whatever the order of the steps.
  • With upsert, rows that were there already give back the id they have, so a load can be run again.
  • Each output is still its own transaction: if the orders fail, the customers stay written. Use upsert on the parent to run it again.
  • In the designer the new columns are there to wire up but empty, since nothing is written until the job runs.
  • A dry run writes the parent rows and takes them back, so it does not try the child rows against their table: their parents are not there. The report says so for that output. Its rows still go through the project's checks.

Limits

  • On SQL Server, getting columns back does not work for a table with triggers.
  • The browser build writes to SQLite files but cannot write to a database server yet; it says so when such a job is run. Use the desktop app or dbdb-cli.
