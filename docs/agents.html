Building a dbdb project: a guide for AI assistants

The guide an assistant reads: steps, the project file and every command. dbdb-cli guide prints it.

You have dbdb-cli and some input files, and someone asked for a project that turns those inputs into outputs. This page is all you need for that: the steps to take, the format of a project file, and every command that changes one. dbdb-cli guide prints it; the binary carries it, so it always matches the version you run.

Other parts of the guide:

dbdb-cli guide expressions       the language of Map columns and Filter conditions
dbdb-cli guide parameters        ${name} in paths and connections, and environments
dbdb-cli guide database-output   writing to PostgreSQL, SQL Server and SQLite tables
dbdb-cli guide compare           checking a target against its source after a load
dbdb-cli guide schedules         running a job by itself, at set times, on one machine
dbdb-cli guide remote-runs       asking another machine to run a job, and being the machine that runs
dbdb-cli guide rest              sources that read a REST API or an OData service: rows, pages, the key
dbdb-cli guide push              a job that sends its result to another machine, as a file in its Incoming folder
dbdb-cli guide html-output       an output that fills a template with rows and writes HTML, as one file or a file for each row or group

What a project is

A project is one JSON file. It names sources (files, sheets, tables or queries to read) and holds jobs. A job is a graph of steps joined by wires: rows enter at Input steps, pass through steps that filter, join and reshape them, and leave at output steps that write files or database tables. The same file opens in the desktop app (dbdb-app), where the person you work for will look at what you built.

Everything in a table is text, and an empty value is the same as a missing one. Types matter only where an output has them (JSON, Excel, SQLite, Parquet, a database) and in expressions that convert.

The way to work

Work in the project's folder, and keep inputs and outputs below it. Paths in the project file are relative to that folder, so the folder can be zipped and handed over.

cd migration                  # holds project.json, Inputs/, Outputs/

  1. Look at the inputs before designing anything.

    dbdb-cli list Inputs/master.xlsx            # sheets, or tables of a database
dbdb-cli preview Inputs/master.xlsx --sheet Parts
dbdb-cli preview Inputs/legacy.sqlite --table orders --limit 5
dbdb-cli preview Inputs/legacy.sqlite --sql "SELECT status, count(*) FROM orders GROUP BY 1"
dbdb-cli preview Inputs/stock.csv --delimiter ';' --encoding windows-1250
dbdb-cli schema Inputs/schemas/XPART.xml    # a fixed-width layout

    The header line of a preview gives each column's name and type.

  2. Add the sources and jobs with apply. One call takes one command or a JSON list of them; a list is all or nothing. Pass a long one through a file or standard input so the shell does not mangle it:

    dbdb-cli apply project.json --quiet @commands.json
dbdb-cli apply project.json --quiet <<'EOF'
[{"command": "add_source", "name": "parts",
  "source": {"kind": "csv", "path": "Inputs/parts.csv"}}]
EOF

    The file is created when it is not there. Without --quiet, apply prints the whole project afterwards.

    You may also write or edit project.json directly; it is the same data. apply has two advantages: it refuses a command that does not fit, saying which field is wrong, and the app can undo what it did.

  3. Check the project.

    dbdb-cli validate project.json

    This first checks the file alone (a step without an input, a wire to a step that is not there, a name nothing answers to) and names every such problem with its job and step. Then it reads every source and does a dry run of every job, which writes nothing. It exits with 0 when all is well, 1 on warnings and 2 on errors. --no-data stops after the first part, for when the databases are out of reach.

  4. Look at the rows where the result surprises you.

    dbdb-cli show project.json                       # every job's steps with their ids
dbdb-cli show project.json --columns-used        # the columns the jobs use of each source
dbdb-cli preview project.json --source parts
dbdb-cli preview project.json --job "Export parts" --step 4
dbdb-cli preview project.json --job "Export parts" --step 2 --output rejected

    --step shows the rows coming out of that step, so you can follow a flow from its input to the step where the rows go wrong.

  5. Run it, when asked to, and report what the run said.

    dbdb-cli run-job project.json "Export parts" --dry-run   # checks, writes nothing
dbdb-cli run-job project.json "Export parts"

    Exit status 0 means written without issues, 1 that the written data has issues (the first 1000 of each output are listed, and all are counted; --all-issues lists every one), 2 that the job failed. A run that writes leaves a record in a runs folder beside the project.

To change a job later, print it, edit the JSON and send it back:

dbdb-cli show project.json --job "Export parts" > job.json
# edit job.json, wrap it as {"command": "update_job", "job": ...}

Things that go wrong

  • Paths. In the project file a relative path is taken from the project file's folder. In a command given to apply it is taken from the directory you run dbdb-cli in. Run it in the project's folder and the two are the same. A file outside the project's folder is saved by its full path, which only computers that have that very path can read: C:\data\x.csv names nothing on macOS or Linux, and /data/x.csv nothing on Windows. check warns of both, and of a name whose capital and small letters differ from the disk's, which only Linux minds.
  • Unknown fields are refused, not ignored, in sources, steps and commands. Read the error: it names the field and lists the ones allowed.
  • Column names are exact, with their case and spaces. Take them from preview, not from memory.
  • An input takes one wire. To put two flows together use an append step (rows under rows) or a join (columns beside columns).
  • A fixed-width output takes its columns by name from the schema. Put a map step before it that makes exactly those names.
  • Passwords stay out of the project: give a connection as env:NAME and it is read from that environment variable when connecting.
  • If the project is open in the desktop app while you change the file, the person has to reopen it there.

The project file

{
  "sources": [
    {"name": "parts", "source": {"kind": "csv", "path": "Inputs/parts.csv"}}
  ],
  "rules": {"rule": [
    {"type": "matches", "column": "part_no", "regex": "^[A-Z]{2}-\\d{4}$"}
  ]},
  "parameters": [{"name": "out", "value": "Outputs/test"}],
  "environments": [{"name": "production", "values": {"out": "Outputs/live"}}],
  "relations": [],
  "key_files": [],
  "perspectives": [],
  "jobs": [
    {
      "name": "Export parts",
      "nodes": [
        {"id": 1, "pos": [40, 40], "step": {"type": "input", "source": "parts"}},
        {"id": 2, "pos": [290, 40], "step": {"type": "write", "path": "${out}/parts.json", "format": {"kind": "json"}}}
      ],
      "wires": [{"from": 1, "to": 2}]
    }
  ]
}

Every part may be left out when empty. perspectives are the saved views of the app's data browser and relations its join suggestions; a job needs neither.

A file that dbdb saved begins with "format": 1, the number of the file format (2 once it holds connectors, 3 once it holds schedules, 4 once it holds a vault, 5 once a job pushes a file to another machine, 6 once it holds a connector to a database or a machine's own setting in a connector, 7 once it holds an HTML output step, a REST API or OData source, or a connector to one, 8 once an OData source gives a row for each related row or reads only what changed), and each source, job and view in it has an id. Leave both as they are when you change a file by hand. A file you write yourself needs neither: without the number it is read as format 1, and the next save adds both. A dbdb that meets a higher number than it knows does not open the file and does not save over it; the error says that a newer dbdb is needed.

Sources

A source is {"name": ..., "source": {"kind": ..., ...}}. Job steps name sources by name.

kind Fields Notes
csv path, delimiter (,), header (true), encoding (utf-8) Any one-character delimiter: "\t", ";". Encodings by their usual names: windows-1250, iso-8859-2, utf-16le…
excel path, sheet, header (true) .xlsx, .xlsm, .xlsb, .xls, .ods
json path An array of objects, or one object per line
parquet path The columns and their types are the file's own; a list or struct comes as text. Compressed with snappy, gzip, LZ4 or brotli, not zstd
fixed_width path, schema, format Laid out by a schema file; see below
sqlite_table / sqlite_query path, and table or sql
access_table / access_query path, and table or sql .mdb, .accdb; a query is SQLite's SQL
postgres_table / postgres_query url, and table or sql postgresql://user@host/db, or env:NAME
sql_server_table / sql_server_query url, and table or sql An ADO.NET connection string, or env:NAME
mysql_table / mysql_query url, and table or sql MariaDB or MySQL: mysql://…, or env:NAME
oracle_table / oracle_query url, and table or sql Experimental
rest url, path, rows, paging, body What a REST API answers to a GET, as JSON (to a POST that sends the JSON text body, where the machine's DBDB_REST_POST lists the host): url is its address or a connector to it, path what follows, rows where the rows are in the answer (data.items; empty when the answer is the list), paging how its pages follow. dbdb-cli guide rest has the ways of paging and the key
odata url, set, query, each, changes An entity set of an OData service (version 2 or 4): url is the service's address or a connector to it, set the entity set, query the query options the service applies ($filter=Year eq 2026&$select=ID,Total; may be left out). each (may be left out) names a list of related rows that $expand in the query brings along, and gives a row for each of them. changes (may be left out) makes a run read only what is new since the run before: {"newer_by": "ChangedAt"} the rows with a larger value in that column, "delta" what the service says has changed, behind its delta link. Rows and pages need no settings. dbdb-cli guide rest has the rest

Defaults are in brackets. A table is name or schema.name. A query is one read-only SELECT; it is often the simplest way to join and filter tables of one database before a job sees them.

Jobs, steps and wires

{"command": "add_job", "job": {
  "name": "Export parts",
  "nodes": [
    {"id": 1, "pos": [40, 40],  "step": {"type": "input", "source": "parts"}},
    {"id": 2, "pos": [40, 150], "step": {"type": "input", "source": "suppliers"}},
    {"id": 3, "pos": [290, 40], "step": {"type": "join", "main_column": "supplier_id", "lookup_column": "id"}},
    {"id": 4, "pos": [540, 40], "step": {"type": "filter", "condition": "status <> 'SCRAPPED'"}},
    {"id": 5, "pos": [790, 40], "step": {"type": "map", "columns": [
      {"name": "part_no",  "value": {"type": "column", "column": "part_no"}},
      {"name": "supplier", "value": {"type": "expr", "expr": "upper(trim(name))"}},
      {"name": "source",   "value": {"type": "constant", "text": "LEGACY"}}
    ]}},
    {"id": 6, "pos": [1040, 40],  "step": {"type": "write", "path": "Outputs/parts.csv"}},
    {"id": 7, "pos": [790, 150],  "step": {"type": "write", "path": "Outputs/scrapped.csv"}}
  ],
  "wires": [
    {"from": 1, "to": 3, "port": 0},
    {"from": 2, "to": 3, "port": 1},
    {"from": 3, "to": 4},
    {"from": 4, "to": 5},
    {"from": 5, "to": 6},
    {"from": 4, "to": 7, "from_port": 1}
  ]
}}
  • A node's id is a whole number of your choosing, unique within its job.
  • pos is where the step sits on the app's canvas: [x, y] of its top left corner. Lay a flow out left to right, 250 apart, and put a branch 110 lower, so that the person opening the job can read it. Steps without pos all pile up in one corner.
  • A node may carry a description: a sentence on what the step is for, for the people who read the job later. It changes nothing about what the step does. With "show_description": true the step shows it on the canvas and grows to fit it. size, [width, height], is the size someone dragged the step to; leave it out and the step sizes itself.
  • A wire goes from output from_port of step from to input port of step to. Both are 0 unless given. An output may feed several steps; an input takes exactly one wire.
  • Only steps that lead to an output step run. validate warns about the others.

The steps

Inputs and outputs are numbered from 0 in the order given.

type Does Inputs Outputs
input reads a source none out
files reads a file, or the files of a folder, one row for each file none out
filter keeps some rows in out, rejected
sort orders rows in out
dedupe keeps the first row of each group of equal rows in out
join adds the columns of matching lookup rows main, lookup out, unmatched
append puts the second input's rows under the first's first, second out
aggregate makes one row of each group in out
map builds the columns of its output in out
output writes a fixed-width file in rejected
write writes CSV, JSON, Excel, Parquet or an SQLite table in rejected
database writes into a table of a database in rejected, written
write_files writes one file for each row in none
html fills a template with the rows and writes HTML in none
push writes a file and sends it to another machine in rejected
prompt asks a model for rows in 1, in 2, in 3, in 4, in 5, in 6, in 7, in 8 out
run_job runs another job of the project after out

Their settings, with the defaults in brackets:

input: source, the name of a project source.

filter: condition, an expression that must hold (see guide expressions), and filters ([]), simple tests that must all pass:

{"type": "filter",
 "condition": "to_int(qty) > 0 and status in ('A', 'B')",
 "filters": [
   {"type": "one_of",   "column": "site", "values": ["ZRH", "GVA", null]},
   {"type": "none_of",  "column": "kind", "values": ["TEST"]},
   {"type": "contains", "column": "name", "text": "valve"},
   {"type": "range",    "column": "year", "min": "2020", "max": null}
 ]}

null in a list of values stands for an empty value. The rows that are not kept leave by the rejected output, with the same columns.

sort: keys, a list of {"column": ..., "descending": false}. Numbers come first, in the order of their value, then the other texts in the order of their characters, then the empty values. A descending key turns all of that round, so there the empty values come first.

dedupe: columns ([], meaning all): rows with equal values in these columns are one group, and the first of each is kept. Sort before it to choose which one that is.

join: main_column, lookup_column, more ([]), inner (false). Each main row gets the columns of the lookup rows whose lookup_column equals its main_column; a main row with several matches comes out once for each. The result has the main columns, then the lookup columns. A main row without a match is kept with empty lookup columns, or dropped with "inner": true; either way it also leaves by unmatched, as it came in. For a key of several columns add the other pairs: "more": [{"main": "site", "lookup": "site_code"}].

A key matches as text, letter for letter, and an empty key matches nothing, not even an empty key on the other side: see "How values compare" below before you join on a column that may be empty or that holds numbers.

append: no settings: {"type": "append"}. Columns are matched by name; a row is empty in the columns its input lacks.

aggregate: group_by ([], meaning one group of all rows) and columns:

{"type": "aggregate", "group_by": ["aircraft"], "columns": [
  {"name": "legs",       "function": "count"},
  {"name": "hours",      "function": "sum", "column": "block_hours"},
  {"name": "last_date",  "function": "max", "column": "flight_date"}
]}

The functions are count, count_distinct, sum, avg, min, max, first and last. count without a column counts rows; the others skip empty values. The result has the group_by columns, then these.

map: columns, the columns of the result in order. Each is {"name": ..., "value": ...} with a value of one of three kinds:

{"type": "map", "columns": [
  {"name": "id",    "value": {"type": "column", "column": "part_no"}},
  {"name": "kind",  "value": {"type": "constant", "text": "PART"}},
  {"name": "price", "value": {"type": "expr", "expr": "to_decimal(price, 2)"}}
]}

Columns that are not listed are dropped. An expression may use the columns of the step's input, not the other new columns.

output: path, schema, format. Writes a fixed-width file laid out by a schema file; see below.

write: path and format:

{"type": "write", "path": "Outputs/parts.csv", "format": {"kind": "csv", "delimiter": ";", "header": true, "encoding": "windows-1252"}}
format Fields
{"kind": "csv"} delimiter (,), header (true), encoding (utf-8)
{"kind": "json"} lines (false): one object per line instead of an array
{"kind": "excel"} sheet (Sheet1); always .xlsx
{"kind": "sqlite", "table": ...} append (false): otherwise the table is made anew
{"kind": "parquet"} compression (snappy): or gzip, lz4, none

Without format it writes CSV. Folders that are missing are made.

A Parquet file has one type for each column, the one the column has in the flow: whole numbers for id_Long, id_Integer, id_Short and id_Byte, floating point for id_Double and id_Float, booleans, and for id_Date a day (2026-01-31), a day and time (2026-01-31 12:30:00), or a moment (2026-01-31 12:30:00+01:00, kept in UTC), whichever the first rows hold. An id_BigDecimal is an exact decimal when the column has a length and a precision, and text otherwise. The other formats write a value that is not of its column's type as text; Parquet cannot, so such a value stops the run and the error names its row and column. A dry run finds it too. Convert the value in a Map step first, or give the column the type id_String.

database: see guide database-output.

files: path, a file or a folder; pattern (every file), which files of a folder to read by name, such as "*.md" or "*.md, docs/*.txt"; names_only (false); pdf_pages (false). It reads files of any kind, where a source reads a table. Each file of the folder, and of the folders below it, is one row:

Column Holds
path the file's place below the folder, with /: 2026/notes.md
name the last part of that: notes.md
size its size in bytes
content what is in the file
encoding text, or base64 when the file is not UTF-8 text and content is its bytes in base64

With names_only the files are listed and not read, and the last two columns are left out.

A PDF is not text, so it is one row with base64 like a picture. With "pdf_pages": true it is one row for each of its pages instead: content is the text of the page, encoding is text, and a sixth column page, between size and content, has the page's number from 1 (empty for the files that are not PDFs). The text is taken out of the PDF on this machine. A scanned page has no text and an empty content. Use it for a long PDF that goes to a prompt step with batch set: see there.

{"type": "files", "path": "Inputs/manuals", "pattern": "*.pdf", "pdf_pages": true}

write_files: path and to (folder). With "to": "folder" each row becomes a file below the folder path: the row's content column is what the file holds and its path column the file's place below the folder. With "to": "file" the step takes one row and writes its content as the file path. A row whose encoding column says base64 is written as the bytes its content stands for. The files take their places when the whole job has run; a file that is there under another name is left alone, and nothing is deleted. A row whose path leads out of the folder (../x, /etc/x) stops the run, and so do two rows with the same path.

{"type": "files", "path": "Inputs/notes", "pattern": "*.md"}
{"type": "write_files", "path": "Outputs/summaries"}

html: path, template and name. Fills template, a MiniJinja (Jinja) template, with the rows and writes the result as the file path. The template is given rows, row (the first row), columns (the column names) and params; a column is row.id, or r.id inside {% for r in rows %}, never id by itself. Values are escaped for HTML. With name set, path is a folder and name a template for each row's file name below it: rows with one name make one file. Do sums in the steps before. See guide html-output.

{"type": "html", "path": "Outputs/report.html", "template": "{% for r in rows %}<p>{{ r.id }}</p>{% endfor %}"}

push: machine, name and format ({"kind": "csv"}). Writes the input's columns as a file, in a format of write, and sends the file to the machine called machine, which saves it as name in the folder Incoming beside its project file. name is a file name, never a path. The other machine has to be there when the job runs, with dbdb-cli runner or the app with Run what is asked ticked; a dry run sends nothing and does not need it. See guide push.

{"type": "push", "machine": "etl-box", "name": "customers.csv"}

prompt: asks a model for rows, through one of the project's AI connectors.

{"type": "prompt", "connector": "local",
 "prompt": "Write one summary of these notes, as summary.md."}
  • connector: the name of a connector of the project.
  • prompt: the task. ${name} in it is a parameter.
  • columns ([]): the columns of the rows the step gives. Leave it empty unless a later step needs certain names.
  • batch (0): how many rows of the first input go into one question. 0 sends every input whole, in one question, which suits a table a model can read in one go and a task that needs all of it (a summary). A number asks about the rows that many at a time, one question for each batch, and puts the answers after each other: a table of any size goes through, for work done row by row (sort into classes, translate, pull values out of text). The other inputs go whole with every question. The model never sees two batches together.
  • max_rows (0, no limit) and too_many (stop): the most rows of one input that are sent, and what happens with more: stop ends the run before the model is asked, send_first sends the first rows and tells the model how many there were. One question holds at most 400,000 characters of rows whatever max_rows is; too_many says what happens past that too.

A prompt step takes the inputs that are wired to it, from none to eight; wire the first to input 0, the next to input 1. Its one output goes to one step. When the job runs, the model is sent the prompt, the columns and rows of every input with the step each comes from, and what the step after it is and needs, so the prompt does not have to describe formats:

  • wired to write_files, the model gives path and content for each file, of whatever kind serves the task: Markdown, CSV, HTML, SVG;
  • wired to output, it gives the columns of the schema file, within their widths;
  • wired to database or write, it gives rows of values for the table or the file, and chooses the columns unless columns names them.

When what the prompt asks for does not fit the step after it (a picture, and the rows go into a database table), the model says so and the run stops with its explanation, before anything is written. dbdb checks the answer too: it has to be the columns asked for, with a value for each in every row. After that the output step checks the rows as it checks any others.

PDFs. A files step wired to a prompt step gives a PDF in one of two ways, and the prompt step sees to the rest:

  • Whole, one row for each PDF (pdf_pages off). A connector that is Claude, with an API key or through Claude Code, is sent the file itself: the model reads each page as a picture with its text, so tables, diagrams and scans are read too. One question takes at most 600 pages and 30 MB of PDFs, and a page costs far more than its text alone. Any other connector (Ollama, llama.cpp, Copilot) is sent the text of all the pages in place of the file, which counts against the 400,000 characters; a PDF without text, such as a scan, stops the run there.
  • By pages ("pdf_pages": true on the files step), with batch on the prompt step: 20 pages a question, say. This works with every connector and for a PDF of any length, and is the cheaper way for a document that is text. The model never sees two batches together, so ask for what a page or a few pages can answer (pull out every field that is described), not for a summary of the whole.
{"type": "prompt", "connector": "local", "batch": 20,
 "prompt": "List every field these pages describe.",
 "columns": ["record", "field", "type", "start", "length", "description"]}

Things to know:

  • A connector that is Claude Code or Copilot starts that program on the machine for each question, signed in as the person is. The first question shows whether it is installed and signed in.
  • The rows of the inputs are sent whole, in one message. A prompt step is for a table a model can read in one go, not for a million rows: put a filter or an aggregate before it. All inputs together may hold 400,000 characters.
  • What is sent leaves the machine unless the connector is a model on the person's own machine (Ollama, llama.cpp). validate warns about a prompt step whose rows go to a service.
  • A step preview (show --step) of a prompt step, or of a step after it, does not ask the model and says so. A dry run does ask: it costs what a run costs, and writes nothing.
  • validate --data leaves out a job with a prompt step for the same reason, and says so.
  • Each run asks again, and the answer may differ from the last one.

run_job: job, the name of another job, and stop_on (warnings). A job of run_job steps wired one after another runs a series: the usual way to offer "run everything". With "stop_on": "warnings" the series stops when that job fails or its data has issues; with "errors" only when it fails. run_job steps are wired only to each other.

Rejected rows

Every output step checks what it writes: the keys and mandatory columns of its schema, and the project's rules. With nothing wired to its rejected output, rows with problems are written anyway and reported as issues. Wire rejected to a write step and those rows go there instead, with two more columns, rejected_row and rejected_because.

How values compare

Do not try these out: they are the rules, and a test holds the engine to them on every build. They are not the rules of SQL.

Empty. A value is text or empty. An empty text and a missing value are the same thing, from any source. A value of spaces is not empty: trim it first if it should count as empty.

In a join, a dedupe, the group_by of an aggregate and a unique rule or key, values are equal when their text is the same, character for character. 7, 007 and 7.0 are three values there, and so are A, a and A with a space after it. Make the two sides alike in a map step before the step: trim(code), upper(code), to_int(id).

What an empty value does there differs by step:

Step An empty value
join matches nothing. A main row with an empty key is kept without lookup columns (dropped with inner) and leaves by unmatched; a lookup row with an empty key is never used. With a key of several columns, one empty part is enough.
dedupe equals another empty value: rows with an empty key are one group, and the first is kept.
aggregate equals another empty value in group_by: such rows are one group. In a function it is skipped, and count with a column does not count it.
unique rule, schema key equals another empty value: two rows with an empty key are a duplicate.
sort comes last, and first with descending.

To join the rows with an empty key too, give both sides a value that stands for empty first: coalesce(code, '-').

In an expression, =, <>, in and the like compare two numbers as numbers, so 7 = 7.0 holds, and everything else as text. A whole number written with leading zeros, such as 007, is text. An empty value:

Expression, with x empty Gives
x is null, x = '', x = null true
x <> 'A', x not in ('A', 'B') true: SQL would drop the row, dbdb keeps it
x in ('A', null) true
x < 5, x >= 5 and the like false, both of them
x || '-', concat(x, '-') -: the empty side adds nothing
x + 1, x * 2 empty
upper(x), trim(x), substr(x, 1, 2) empty
length(x) 0
to_int(x), to_date(x, ...) empty; only a value that is there and cannot be converted stops the run

There is no third answer "unknown": a condition holds or it does not, and not of a comparison that is false is true.

Fixed-width files and schema files

A fixed-width file (source or output) is laid out by a schema file in the XML that Talend and Talaxie export. To make one, write it:

<?xml version="1.0" encoding="UTF-8"?>
<schema>
    <column label="part_no" talendType="id_String" length="12" key="true" nullable="false"/>
    <column label="description" talendType="id_String" length="40" nullable="true"/>
    <column label="qty" talendType="id_Integer" length="6" nullable="true"/>
</schema>
  • label is the column's name and length its width in characters. Every column of a fixed-width file needs a length.
  • key="true" columns together must be unique, and nullable="false" columns must have a value. An output reports the rows that break this.
  • The types are id_String, id_Integer, id_Long, id_Double, id_BigDecimal, id_Date and id_Boolean.

An output step takes the schema's columns by name from its input and writes them in the schema's order; an input column the schema does not have is left out, and a schema column the input does not have is an error. format (all optional) says how values are placed:

{"type": "output", "path": "Outputs/XPART.txt", "schema": "Inputs/schemas/XPART.xml",
 "format": {"overflow": "fail", "align": "left", "pad": " ", "line_ending": "\r\n",
            "final_newline": true, "encoding": "windows-1252",
            "columns": {"qty": {"align": "right"}, "description": {"overflow": "truncate"}}}}

overflow says what happens to a value wider than its column: fail (the default: the run stops), truncate (cut silently) or warn (cut and reported as an issue).

Rules

Rules are checks on the data that a schema cannot express. Every output applies the rules that name columns it has.

[
  {"command": "add_rule", "rule": {"type": "unique", "columns": ["part_no", "site"]}},
  {"command": "add_rule", "rule": {"type": "matches", "column": "part_no", "regex": "^[A-Z]{2}-\\d{4}$"}},
  {"command": "add_rule", "rule": {"type": "required", "column": "closed_on", "when": {"column": "status", "one_of": ["CLOSED", "CANCELLED"]}}},
  {"command": "add_rule", "rule": {"type": "empty", "column": "closed_on", "when": {"column": "status", "equals": "OPEN"}}}
]

when is optional and tests another column of the same row with equals, one_of or present (true: has a value). In the project file the rules are the list under "rules": {"rule": [...]}.

Parameters

${name} in a path, connection, table name or expression is replaced by the parameter's value, and an environment gives other values for a run (run-job --env production --param name=value). ${today()} and other formulas work in paths too. See guide parameters.

{"command": "set_parameters",
 "parameters": [{"name": "out", "value": "Outputs/test"}, {"name": "db", "value": "env:TEST_DB"}],
 "environments": [{"name": "production", "values": {"out": "Outputs/live", "db": "env:PROD_DB"}}]}

set_parameters replaces all parameters and environments at once.

A layout for the app

A project can carry a layout of the app's window. It changes nothing about the data, and the app shows it only to a person who ticked View > Load project layouts when opening, so write one only when you are asked to.

{"command": "set_layout", "layout": {
  "workspaces": [
    {"name": "Load", "root": {"row": [
      {"share": 0.25, "tabs": [{"kind": "sources"}]},
      {"share": 0.75, "column": [
        {"tabs": [{"kind": "designer", "job": "load parts"}]},
        {"tabs": [{"kind": "issues"}, {"kind": "notes", "note": "Plan"}]}
      ]}
    ]}}
  ],
  "active": "Load"}}

A tile is a row of tiles side by side, a column of tiles one above the other, or tabs, a group of panes; share is its part of the row or column, and active the tab that shows, counted from 0. A pane has a kind (sources, browser, query, designer, graph, preview, issues, log, runs, compare, assistant, notes, keys, connectors, schedule, api), and may name what it shows: job for a designer, view for a browser, source for a graph or an API Call Builder (api), settings.key_file for a graph of one of the project's key files by itself, comparison for a compare, note (its path) for notes. title gives its tab a name. Workspaces need names of their own. set_layout replaces the whole layout, and renaming a job, view, source, comparison or note keeps the panes pointing at it.

A connector is what the project reaches outside itself: a model, for the app's Assistant and a Prompt step, a database, for the sources and database outputs that read through it, or a REST API or an OData service, for the sources that read it. It is the person's to set up; add or change one only when asked. {"name": ..., "kind": "ollama" | "llama_cpp" | "claude" | "claude_code" | "copilot", "address": ..., "model": ..., "key_variable": ..., "instructions": ..., "machines": [...]}: only name and kind are needed. key_variable is the name of an environment variable and never a key, which is refused. machines names the computers the connector is for; left out, it is for every machine that opens the project. dbdb-cli connectors project.json lists them and says which this machine may use.

A connector to a database is {"name": "warehouse", "kind": "postgres" | "sql_server" | "mysql" | "oracle" | "sqlite" | "access", "address": ...}: address is the connection as a source writes it (a connection string, env:NAME, or the file of an SQLite or Access database), and it takes no model, key or instructions. A source or a database output reads through it by writing ${connection:warehouse} as its url (or path). The tools that take a location (list_tables, preview, database_catalog, guess_keys, snapshot_database) take it too, and fill it in from the project. Use one when several sources read one database, and never write a password into it: ${vault:name} or env:NAME, as in any connection. validate says when something reads through a connector the project does not have, or one of another kind of database.

A connector to an OData service is the same with "kind": "odata", and a source of kind odata reads through it.

A connector to a REST API is {"name": "shop", "kind": "rest", "address": "https://api.example.com/v1", "key_variable": "SHOP_KEY", "key_header": "X-API-Key"}. A source of kind rest reads through it with "url": "${connection:shop}", and gets the key with it. key_variable or key_secret say where the key is, as for a model. key_header says how it is sent: left out or bearer for Authorization: Bearer, basic for a key that is user:password, the name of the header it goes in, or oauth https://login.example.com/token scope to sign in first with a key that is client id:client secret. It takes no model or instructions.

A machine can have its own value for a setting, in local by the machine's name: "local": {"anna-laptop": {"address": "postgresql://etl@localhost:5433/shop"}}. address, model, key_variable, key_secret, key_header and instructions can be given there; what is left out is the connector's own, which every other machine uses. So a database that machines reach at different addresses is one connector. list_connectors shows a connector as the project has it, and under here the settings as this machine has them where it has its own.

A schedule runs a job by itself on one machine: {"name": ..., "job": ..., "machine": ..., "when": {"kind": "cron", "cron": "0 6 * * 1-5"}, "time_zone": "Europe/Zurich"}. when is also {"kind": "once", "at": "2026-11-20 08:00"} or {"kind": "every", "every": 2, "unit": "hours", "from": "2026-11-20 08:00"}. Add or change one only when asked, and ask which machine is to run it. dbdb-cli schedule list project.json says when each runs next, what its last run did and what it missed. A schedule runs only while the app is open on its machine with Run here ticked, or dbdb-cli schedule run project.json is running there. See guide schedules.

The vault holds the project's secrets, sealed with a password the person chose. You cannot read a secret or set one: the vault commands take a value that is sealed already, and only dbdb-cli vault and the app seal. What you can do is use one. Where a connection needs a password, write ${vault:name} in its place (postgresql://etl:${vault:pg_prod}@host/db) and ask the person to run dbdb-cli vault project.json set pg_prod, or write env:NAME for a value of that machine's own. Never write a password into a connection. dbdb-cli vault project.json status lists the secrets by name with what uses each. A run that needs a secret while the vault is locked stops and says so: the person unlocks it, or sets DBDB_VAULT_PASSWORD for the server. key_secret of a connector names a secret that holds its key, in place of key_variable.

A job can run on another machine, one that has the files, network and passwords it needs: dbdb-cli run-job project.json <job> --on <machine> asks the runner there and waits, and the ask_run tool does the same. Only a machine where dbdb-cli runner project.json runs, or the app is open with Run what is asked ticked, takes an ask; dbdb-cli asked-runs project.json (the list_asked_runs tool) says which are here now and what became of each ask. Ask for a dry run first, and for a run that writes only when the person asked for it. See guide remote-runs.

A perspective is a view for the app's browser: {"name": ..., "root": {"source": ..., "filters": [], "sort": [], "hidden": [], "joins": [{"parent_column": ..., "child_column": ..., "node": {...}}]}}. Add one when the person will want to look through joined inputs in the app; a job does not need it.

A comparison checks a load: it reads two sources, matches their rows by key columns and reports the rows that differ or are on one side only, without writing to either. {"name": ..., "left": <source>, "right": <source>, "key": [<left columns>], "columns": [{"left": ..., "right": ..., "exclude": false, "tolerance": "0.01"}]}; only the first three are needed. Run it with dbdb-cli compare project.json <name>, which exits with 1 when the sides differ. See guide compare.

A key file adds what a database does not say about itself: keys it does not declare, and descriptions of tables and columns. One kind does more. A key file with "dbdb:catalog" at the top lists every table, column and key of one database, and the desktop app then shows that database from the file and does not read the database until the person presses ⟳, because reading the tables and keys of a large database takes long. So such a file can fall behind the database. In it, a foreign key with "dbdb:declared": true is one the database itself declared when the file was written; the others were added from elsewhere. The CLI and the MCP tools never take a database's tables from a key file: list, preview, database_catalog and guess_keys always ask the database. When what you build depends on tables or keys being there, confirm the file first:

dbdb-cli check-keys project.json --database orders    # orders: a source of that database
dbdb-cli export-keys project.json --database orders --whole -o orders.keys.json

check-keys reads the database now, prints one line for each table, column or key that differs from the file, and exits with 1 when there is one. export-keys --whole reads the database and writes the file again; add_key_file has a project use it. Tell the person when the file was behind: until they press ⟳ or the file is written again, the app shows them the old tables.

A key file is changed a table at a time, with edit-keys, and never by writing the whole file again: a key file of a large system is megabytes, and a file written whole loses what you did not mean to touch.

dbdb-cli edit-keys extra.keys.json --show notes       # the table as this file has it, its keys numbered
dbdb-cli edit-keys extra.keys.json @changes.json      # a change or a list of them; `-` reads standard input

A change is JSON with an edit field. A list of them is made in order, and nothing is written unless all of them can be made:

[
  {"edit": "add_foreign_key", "table": "notes", "key": {
    "columns": ["owner_id"], "ref_table": "users", "ref_columns": ["id"],
    "when": {"column": "owner_type", "values": ["U"]},
    "description": "Every owner_id of the U rows is a user (checked November 2026)."}},
  {"edit": "set_foreign_key", "table": "notes", "index": 0, "key": {
    "columns": ["owner_id"], "ref_table": "users", "ref_columns": ["id"]}},
  {"edit": "remove_foreign_key", "table": "notes", "index": 0},
  {"edit": "set_primary_key", "table": "notes", "columns": ["id"]},
  {"edit": "set_table_description", "table": "notes", "description": "Remarks on anything"},
  {"edit": "set_column_description", "table": "notes", "column": "owner_type",
   "description": "U for a user, C for a company"},
  {"edit": "annotate_foreign_key", "table": "notes", "key": {
    "columns": ["owner_id"], "ref_table": "users", "ref_columns": ["id"],
    "status": "confirmed", "note": "40 of 40 values found", "tags": ["checked"]}},
  {"edit": "set_table_note", "table": "notes", "note": "Leave out the rows before 2020"},
  {"edit": "set_column_note", "table": "notes", "column": "owner_type", "note": "Never empty"},
  {"edit": "set_table_tags", "table": "notes", "tags": ["wave 1"]},
  {"edit": "set_column_tags", "table": "notes", "column": "owner_type", "tags": ["code list"]},
  {"edit": "set_column_type", "table": "notes", "column": "owner_id", "type": "integer"},
  {"edit": "set_table", "table": "notes", "resource": null}
]
  • when and description of a key may be left out. when is for a column that points to different tables: the key holds for the rows where that column of the same table has one of the values.
  • index is the key's place among the table's foreign keys in that file, from 0. --show numbers them; look before you change or remove one.
  • A description left out or empty takes the description away, and a primary key without columns takes the primary key away.
  • A description says what a thing is. A note is a remark for whoever works on the data (how a key was found, what is still open), and tags are words to find things by. Tables, columns and keys take both. A note left out or empty, and tags left out, take them away.
  • set_column_type says what a column holds, as a Table Schema type. dbdb goes by string, integer and number: a key that joins text to a number is joined with a cast. Without a type, it is taken away.
  • A key has a status: confirmed, doubtful, rejected, or to_check, which is what a key without one is. A rejected key stays in the file and joins nothing: reject a key that was checked and found wrong rather than removing it, so that nobody proposes it again.
  • annotate_foreign_key finds the key by what it joins (its columns, the table and columns it refers to, and its when), not by index. It sets the key's status, note and tags, and its description when one is given. When the file does not have the key, it adds it. Use it to say something about a key of a file that a tool writes: put it in the file kept by hand, and the tool's file stays as it is.
  • Where two key files say something about the same thing, the one the project lists later is heard. The same key in two files is one key, with the later file's status, note and description where it has them, and the tags of both.
  • set_table puts a whole Frictionless resource in the place of everything the file says about a table, and null removes the table from the file.
  • A table the file does not have is added by the first change that adds something to it, and goes again with its last key.
  • Only the table changed is written again. The rest of the file stays as it was, to the letter, with properties dbdb does not know.
  • The answer has each changed table as the file now has it, and undo: the changes that take these back, to hand to edit-keys again.

A key the database does not declare is a guess until the data is asked. check-key asks it:

dbdb-cli check-key project.json --database orders --table notes \
  --key '{"columns": ["owner_id"], "ref_table": "users", "ref_columns": ["id"],
          "when": {"column": "owner_type", "values": ["U"]}}'

It has the database of the source orders count the different values of notes.owner_id, among the rows where owner_type is U, and how many of them are a users.id. Rows with an empty owner_id are left out. The answer has values, found, not_found and all_found, and the exit status is 1 unless every value was found. The first values that were not found go to stderr, for a person; the answer itself never has a value of the data. The key need not be in a key file, so check a guess before adding it. All found does not prove a key: any column of small numbers is found in any other. Few found makes it doubtful. --write extra.keys.json keeps the result with the key in that file, as "checked": {"on": "2026-11-18", "values": 40, "found": 40, "source": "orders"}; the answer's to_keep_it is the same change for edit-keys, and takes a status when the result settles one. The database is only read.

Which file a key goes in matters. A project often has one key file that a tool writes, or that holds a whole database ("dbdb:catalog"), and one kept by hand. The first is written again by its tool and loses what was added to it, so keys you find go in the second. Ask the person which file that is when it is not plain from the names, and say which file you changed. To move a key, remove it from one file and add it to the other.

A database that is slow or will not stay within reach can be copied into one SQLite file, and the work done on the copy:

dbdb-cli snapshot env:ORDERS_DB orders.sqlite                 # a connection string, or a database file
dbdb-cli snapshot project.json orders.sqlite --source orders  # the database a source reads

It copies every table with its rows, its primary key and the foreign keys the database declares, and prints each table with its number of rows. The MCP tool snapshot_database does the same: to export or copy a whole database, or many of its tables, to SQLite, use it rather than a job. Views are left out unless --views is given, --table NAME (repeatable) copies only some, and a file that is there stays unless --replace is given. schema.name becomes name in the copy unless two tables would share a name. A table that cannot be read is named on stderr and the exit status is 1; the others are copied. The database is only read.

Notes are the project's own pages of Markdown, kept in folders: what was decided, what to check, how a load is run. An entry is {"type": "note", "name": ..., "text": ...} or {"type": "folder", "name": ..., "children": [...]}; a path is the names from the top joined by /, such as Migration/Cutover runbook. text may be one string or a list of lines. [[Name]] links to another note, ![[Name]] shows it in place. dbdb-cli notes project.json lists them and --read <path> prints one.

Through MCP instead

dbdb-cli mcp --project project.json serves the same things as tools to an MCP client: guide, list_tables, preview, show_project, apply_command, validate_project, preview_step, run_job and more.

No answer there is longer than a page, so a project of hundreds of jobs is read in parts: project_overview says what it holds, list_jobs and list_sources page through the names (next_offset is the offset of the next page), show_job gives one job's steps with their ids and wires, and show_source one source as the file has it. guide gives a long page as the titles of its sections, and one with section. validate_project takes a job to check that job alone.

list_sources and show_source also say which columns of a source the jobs use (dbdb-cli show project.json --columns-used and --source NAME print the same). It is found by following each job's steps in the file, so no source is read: every column means a step writes the rows as they come, and a column marked unsure is used after a Join of two sources, from this one or from the other. A run asks a database for those columns alone, whatever the source says, so a source that reads a whole table, or SELECT *, need not be changed for speed. To change a source's query for another reason, change_source with {"kind": "postgres_query", "table": null, "sql": "SELECT …"} changes those settings and keeps the connection. Check the job after with validate_project and its job.

check_keys is check-keys there, and database_catalog reads a database's tables and keys from the database itself. What the key files add is not in that answer: describe_table returns one table from the key files, with its description, its columns, its keys with the condition of each conditional key, and the keys of other tables that refer to it. Given a text no table is called, it lists the tables whose name or description contains it. Use it rather than reading a key file, which can hold thousands of tables. check_key is check-key: it returns the counts and never a value. discover_keys is discover-keys: it proposes keys from a database's catalog and checks each against the data; with "from_data": true in its settings it also counts every table's columns and proposes a column whose values fit among another table's different values, for a database whose names say little, which reads every table once. The keys already known propose more: a column with the name of columns that mostly have a key to one table is proposed for it too, and the plan lists, under columns_with_keys_to_different_tables, where the key files disagree. With "ask" in its settings, the name of a connector of the project that reaches a model, that model is asked which keys the names and descriptions make likely, some tables to a question: it is sent names, kinds and descriptions and no rows, what it proposes is checked against the data like the rest, and the_model in the answer says what came of it. Leave ask out unless the person wants a model asked: it sends the database's names to wherever that connector points. Ask with plan_only first, which says how many queries a run makes; to_keep_them in its answer are the changes for edit_key_file, each key to check, with its evidence in a note. import_keys is import-keys: it makes one key file from a folder of XML files that describe a database, such as a vendor's data dictionary with a file for each table. Call it with folder alone first: the answer lists every kind of element by its place, with how often it is there and its attributes, and no value. Write the mapping from that (table is the element there is about one of for each table, the rest are paths from it), call again without output to see what would be made and left out, and then with output to write the file. edit_key_file is edit-keys for a key file of the project, named by its file name: edits are the changes, and table without edits shows that table as the file has it. Use whichever you were given; the project file is the same.

A worked example

Two inputs, Inputs/parts.csv (part_no, name, supplier_id, qty) and Inputs/suppliers.csv (id, supplier), become one JSON file of the parts in stock with their supplier's name, and a CSV file of the parts whose supplier is unknown.

[
  {"command": "add_source", "name": "parts", "source": {"kind": "csv", "path": "Inputs/parts.csv"}},
  {"command": "add_source", "name": "suppliers", "source": {"kind": "csv", "path": "Inputs/suppliers.csv"}},
  {"command": "add_rule", "rule": {"type": "unique", "columns": ["part_no"]}},
  {"command": "add_job", "job": {
    "name": "Parts in stock",
    "nodes": [
      {"id": 1, "pos": [40, 40],   "step": {"type": "input", "source": "parts"}},
      {"id": 2, "pos": [290, 40],  "step": {"type": "filter", "condition": "is_int(qty) and to_int(qty) > 0"}},
      {"id": 3, "pos": [290, 150], "step": {"type": "input", "source": "suppliers"}},
      {"id": 4, "pos": [540, 40],  "step": {"type": "join", "main_column": "supplier_id", "lookup_column": "id"}},
      {"id": 5, "pos": [790, 40],  "step": {"type": "map", "columns": [
        {"name": "part_no",  "value": {"type": "column", "column": "part_no"}},
        {"name": "name",     "value": {"type": "expr", "expr": "title(trim(name))"}},
        {"name": "supplier", "value": {"type": "expr", "expr": "coalesce(supplier, 'UNKNOWN')"}},
        {"name": "qty",      "value": {"type": "expr", "expr": "to_int(qty)"}}
      ]}},
      {"id": 6, "pos": [1040, 40],  "step": {"type": "write", "path": "Outputs/stock.json", "format": {"kind": "json"}}},
      {"id": 7, "pos": [790, 150],  "step": {"type": "write", "path": "Outputs/unknown_supplier.csv"}}
    ],
    "wires": [
      {"from": 1, "to": 2},
      {"from": 2, "to": 4, "port": 0},
      {"from": 3, "to": 4, "port": 1},
      {"from": 4, "to": 5},
      {"from": 5, "to": 6},
      {"from": 4, "to": 7, "from_port": 1}
    ]
  }}
]
dbdb-cli apply project.json --quiet @commands.json
dbdb-cli validate project.json
dbdb-cli preview project.json --job "Parts in stock" --step 5
dbdb-cli run-job project.json "Parts in stock"

When you hand the project over, say what each job reads and writes, what validate and the run reported, and anything in the inputs that the person should decide about (duplicate keys, values that did not convert, rows without a match).
