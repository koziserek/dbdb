Asking an AI assistant for a project

What to ask an AI assistant that has dbdb-cli, to build a whole project.

An assistant that has dbdb-cli (or the MCP server) can build a whole project from your input files. It learns dbdb's format by itself, from dbdb-cli guide (agents.md), so your request does not have to explain dbdb. This page is about what the request does have to say, with a prompt to copy.

What the prompt has to carry

A project file encodes decisions that are in nobody's input files. An assistant can find the joins and the date formats by looking at the data; it cannot find out that helicopter chapters are out of scope, or that the importing system wants ICAO codes where the source has IATA codes. Whatever you would have decided while clicking a job together has to be in the prompt, or the assistant will decide it for you, quietly.

So a prompt that gives a result you can sign off has five parts:

  1. Where the instructions are. One line: run dbdb-cli guide first.
  2. The specification of the outputs. Best as files: the schema XML of each fixed-width layout, whose column comments say what each column holds, or the layout document of the importing system.
  3. The business rules: what is in scope, which codes translate to which, what a date looks like. One line each; these are the lines only you can write.
  4. The conventions: how jobs are named, where outputs and rejected rows go, which parameters there are.
  5. How to work and what to hand over: check after every job, never drop a row without saying so, ask instead of guessing, and report row counts and assumptions.

The last part matters most. "Never drop rows silently" and "write the question down, do not guess" are what separate a migration that can be signed off from one that merely runs, and validate with 0 errors and 0 warnings gives the assistant a test for being done.

A prompt to copy

This one asks for what the Showcase project (Showcase.zip, which the maintainer hands out on request) does, given only the binary and the Showcase's Inputs folder: the workbook, the SQLite database, the airport list and the eight schema files. No project file is given.

You have ./dbdb-cli and a folder Inputs/. Run `./dbdb-cli guide` first and
follow it; read `guide expressions` and `guide parameters` before writing
jobs. Do not write project JSON from memory of other tools.

Goal: a dbdb project, project.json in this folder, that produces one
fixed-width transfer file per layout in Inputs/schemas/*.xml, for the
operator described by the inputs. The schema files are the specification:
column names, widths, keys, mandatory columns, and the comment on each
column says what it must hold (`./dbdb-cli schema FILE` prints them).

Inputs: master_data.xlsx (master data kept by hand), utilization.sqlite
(the operations system), airports.csv (a reference list). Look at every
sheet and table before designing anything.

Business rules:
- XATA: only the chapters for fixed-wing turboprops; titles in capitals,
  cut to the column width; one row per chapter.
- XADDRESS: the address list, plus every airport as an address.
- XAC, XACDAY: aircraft types use the master data's codes, not the ICAO
  designators of the operations system; the Type mapping sheet translates.
  Stations are ICAO codes; the operations system has IATA codes.
- Dates are DD.MM.YYYY in every transfer file.
- Cancelled legs are not utilization.

Conventions:
- One job per transfer file, named after its layout, plus a job
  "Run everything" that runs them one after another and stops on warnings.
- Outputs go to Outputs/${exportsDestination}/, a parameter that is
  dataLoad_001 unless a run says otherwise. The operator's code is a
  parameter too.
- Rows left out on purpose, and rows that fail a check, go to a CSV file
  under rejected/ with the reason. Never drop rows silently.
- Add project rules for every format the layouts imply: the shape of
  codes, date formats, allowed values, columns that are mandatory only in
  some cases.
- Lay the steps out left to right, so that a person can read each job in
  the app.
- Use a query as a source where one database can do the join or the
  running total itself.

Working method: build one job at a time. After each, run `validate` and
preview its steps; fix it until `validate` reports 0 errors and 0
warnings, or stop and tell me why a warning is right. Where a rule above
is ambiguous or the data contradicts it, do not guess: write the question
down, take the cautious reading, and mark it in your report.

Deliver: project.json; the Outputs/ of a real run of "Run everything";
and a report that says, for each job, what it reads, the rows in and out,
what was rejected and why, and every assumption you made.

For your own migration keep the skeleton and replace three things: the goal and the inputs, the business rules, and the conventions you care about.

Through MCP the prompt is the same, with this as its first paragraph:

Use the dbdb tools. Call `guide` first and follow it; read its topics
"expressions" and "parameters" before writing jobs. Check your work with
validate_project and preview_step. Do not write project JSON from memory
of other tools.

What to give it

  • The Linux dbdb-cli of a release, which runs on any distribution with glibc 2.31 or later, so in the usual sandboxes of chat and coding assistants. On your own machine, the one you have.
  • The input files, in a folder Inputs, with the schema files of the layouts to write in Inputs/schemas.
  • No password. For a database, run the assistant on your own machine and give the connection as env:NAME; a sandbox reaches no database of yours.

What to check when it comes back

  • Open the project in the app and read each job; the layout is yours to judge, and the Designer shows the rows at every step.
  • Run dbdb-cli validate project.json yourself.
  • Read the report's assumptions and the files under rejected/ first: the questions a migration raises are there.
  • Compare row counts with what you know of the source.

How far this is tested

The guide's own worked example is built, validated and run by a test on every build. The prompt above has not yet been run against a fresh assistant and compared with the Showcase's outputs file by file; until it has, take it as a well-founded starting point, not a guarantee.
