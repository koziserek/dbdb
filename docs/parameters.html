Parameters and environments

${name} in paths, connections and table names, and environments for test and production.

A parameter is a named value of the project. Write ${name} where the value should go, and one job runs against test data today and production tomorrow without being changed.

"parameters": [
  {"name": "in",  "value": "data/test"},
  {"name": "db",  "value": "env:TEST_DB"},
  {"name": "tag", "value": "T"}
],
"environments": [
  {"name": "production", "values": {"in": "/srv/export", "db": "env:PROD_DB"}}
]

Each parameter has a default value. An environment gives some of them another value; the ones it does not mention keep their default.

Where ${name} works

  • File paths of sources and outputs: ${in}/parts.csv. A path that begins with a parameter is taken from the project's folder unless the value is a full path.
  • Connections, table names, sheet names and queries of sources: ${db}, ${tag}.orders.
  • Expressions in Map and Filter steps, where it is a value: ${tag} || '-' || code.

A name that is not a parameter of the project is an error, so a misspelt ${naem} never becomes part of a file name.

Dates and other formulas in a path

Between the curly brackets there may also be a formula, written as in a Map step (see expressions), with the parameters where a Map step has columns:

Path Written to
out/${today()}/XATA.txt out/2026-09-30/XATA.txt
out/XATA${format_date(now(), 'yyyyMMddHHmm')}.txt out/XATA202609301716.txt
${in}/${upper(tag)}_${format_date(add_days(today(), -1), 'yyMMdd')}.csv data/test/T_260929.csv

A folder that does not exist yet is made. This works wherever ${name} does, except inside an expression, which is a formula already.

The brackets are curly ones. $(name), as a shell writes it, is not filled in, and a file path that has it is refused instead of becoming a folder of that very name.

A password does not belong in a parameter in plain text. A parameter can hold env:PROD_DB, which is read from the variable PROD_DB when connecting, or a connection that takes its password from the project's vault, such as postgresql://etl:${vault:pg_prod}@db/sales (see the vault). An environment can name another secret, so test and production each have their own.

Choosing the values for a run

  • App: Edit > Parameters… (or Parameters… in the Designer) edits the table of parameters and environments. Once there is an environment, the Designer shows an Environment list; previews, checks and runs in every pane use the one chosen there.

  • Command line:

    dbdb-cli run-job project.json export                       # defaults
dbdb-cli run-job project.json export --env production
dbdb-cli run-job project.json export --env production --param tag=X

    --param name=value may be repeated and wins over the environment.

  • MCP: run_job, preview_source and check_source take "environment" and "parameters": {"name": "value"}. The set_parameters command replaces the project's parameters and environments.

A job run as a Sub-job step uses the same values as the job that runs it.
