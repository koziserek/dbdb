Runs on another machine

Asking another machine to run a job, and being the machine that runs it.

A copy of a project can ask another machine to run a job: one that has the files, the network and the passwords the job needs. A page in a browser, which cannot run a job that writes to a database, has one run this way. So does a laptop that should not carry a night's load.

The machine that runs is a runner: dbdb-cli runner with the project, or the app left open there. The copy that asks needs nothing but the project and its sync.

How an ask travels

An ask goes where the changes to the project go: through the sync folder next to the project file, and through the relay of a project that is shared through one (shared-projects.md). The answer comes back the same way. So:

  • no port is opened on the runner, and nothing new listens anywhere;
  • on a relay, an ask is sealed with the project's key like every change;
  • the project has to be synced. A project kept out of the sync (no_sync) can neither ask nor be asked.

An ask is never in the project file. It lies beside the project in what the copies sync, and is forgotten there after a week.

What an ask holds

The job's name, the environment and parameter values the asker chose, whether it is a check only (a dry run), the machine that is asked and the machine that asks. Passwords do not travel: a connection that reads env:NAME reads it on the machine that runs.

The runner runs the job as the copies have it at that moment. A change that has not reached the runner yet is not in the run.

Being a runner

A machine runs what is asked of it only after its user said so, there, for that project. A project file that someone sent starts nothing.

  • dbdb-cli runner project.json stays, synced with the project's other copies, and runs both this machine's schedules (schedule.md) and what is asked of this machine. Unlike schedule run it follows what other copies change through the relay too, so a schedule edited in a browser is the one that runs. --no-schedules and --no-asked leave one of the two out, --no-relay keeps it to the sync folder, and --machine NAME makes it the runner of another name.
  • The app, while it is open with the project, once Run what is asked is ticked in the Job schedule pane. The tick is for this copy and this project, saved with the app and never in the project. The app says so each time the project is opened, and asks again when the project is no longer the one the tick was given for (sharing-and-trust.md).

Whoever has the project file can ask a runner of that project. That is no more than they could do already: they could change the job.

So a runner runs whatever jobs the project holds, as the user it runs as, for everyone who has the project file. Before you start one on a machine that is not yours, read What sharing a project allows: what a job can read and write there, and how to give a runner a user, a folder and a database user of its own.

A runner runs one job at a time. A schedule that comes due during a run starts when that run is over. So does what is asked, if the run is over within the quarter of an hour an ask waits (see below); the runner takes an ask only when it can start it.

dbdb-cli runner stays in the foreground and writes a line for each run to standard error. To keep it running, hand it to the system:

# systemd: ~/.config/systemd/user/dbdb-runner.service
[Unit]
Description=dbdb runner for the ETL project
After=network-online.target

[Service]
ExecStart=/usr/local/bin/dbdb-cli runner /srv/etl/project.json
# The passwords the project reads as env:NAME, in a file only this user reads.
EnvironmentFile=%h/.config/dbdb/etl.env
# Environment=DBDB_MACHINE=etl-box
Restart=on-failure

[Install]
WantedBy=default.target

A user's service runs only while that user is logged in, and does not start with the computer, unless the system is told otherwise once: sudo loginctl enable-linger $USER. network-online.target means nothing to a user's service; a runner that starts before the network tries the relay again by itself.

A machine that only got the project file of a shared project takes the project from its relay when the runner first starts, as the app does.

Asking

  • The app, and the page in a browser: Run on… in the Job designer lists the machines that have a runner here now, each with Check and Run. The run uses the environment chosen in the designer. The status bar says what becomes of it; the menu shows what was asked from here and is not over, and takes back an ask that no runner has taken.
  • The command line: dbdb-cli run-job project.json load --on etl-box asks and waits. It writes each step to standard error and exits as run-job does: 0, 1 when the written data has issues, 2 when the run failed or nobody took the ask. --no-wait prints the ask's id and exits. --dry-run, --env and --param mean what they mean here.
  • An assistant: the ask_run tool, with wait_seconds to wait for the end, and list_asked_runs for what became of it.
dbdb-cli asked-runs project.json                 # what was asked, and the runners here now
dbdb-cli asked-runs project.json --json
dbdb-cli asked-runs project.json --take-back ID  # before a runner took it

What becomes of an ask

State Meaning
waiting No runner has taken it yet
running A runner took it and has not said how it ended
done It ran: the record says how
expired No runner took it within 15 minutes. It will not run
taken back The asker took it back before a runner took it

Not later. An ask waits 15 minutes for a runner. A runner that starts tomorrow does not run what was asked today. The clocks of the two machines have to agree to within that quarter of an hour.

Once. A runner takes an ask before it runs it, waits two seconds, and runs only if the ask is still its own. Of two runners on machines of one name that take it at the same moment, the copies agree on one. Two runners that cannot hear each other for longer than that, as with one of them cut off from the relay, can both run it.

A runner that stops. A run that was going on when its runner was stopped stays "running": the runner is not there to say more. Ask again.

How far a run is

While it runs what was asked, a runner says how far the run is: the job it is in, and the rows read and written so far. Where the ask is shown, "running" becomes

load on etl-box: running, 1200 rows read, 1100 written

in the "Run on" menu of the app, in "Who else is here" beside the runner, and in the lines dbdb-cli run --on prints while it waits. The numbers follow the run about once a second; the command prints a line at most every five seconds.

This goes the way "who else is here" goes, to the copies that are there at that moment, and is kept nowhere: not by the relay, not in the sync folder beyond the small file a copy rewrites while it is there, and not in what the copies sync. A copy that opens the project later sees "running" and then the numbers of that moment. A copy older than this shows "running" alone.

The record

The run is recorded on the machine that ran, in the runs folder beside its project file, like a run made there (runs.md), with machine and, under asked, the ask and who asked. A check leaves no record there, as a check made by hand leaves none.

The record also goes back to the asker with the answer, and shows in the Runs pane of every copy while the ask is kept: a week. A record of more than 32 KB goes back without the lines of its issues; their count stays, and the whole record is on the machine that ran.

The runs a runner makes for a schedule are not sent back this way: a schedule that runs every minute would add to what the copies sync without end. Copies that share only a relay still see each other's scheduled runs only where the runs folder is shared.

Files for another machine

A runner also takes the files that jobs on other machines push to it, into the folder Incoming beside its project file: see push.md.

Not yet

  • No way to stop a run from the asker's side. It can be stopped on the machine that runs it.
  • A runner started by dbdb-cli runner keeps no log of its own beyond what it writes to standard error; the system that starts it keeps that.
